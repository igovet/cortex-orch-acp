# Architecture overview

Cortex is an incoming ACP v1 stdio agent, the Rust binary `cortex-acp` (`crates/cortex-acp`). It runs its own project-local runtime and starts Codex or Claude ACP engines, or the optional OpenCode v2 engine, as outgoing sessions. Models propose work and interpret evidence; the runtime owns lifecycle, dependency scheduling, rights, routing, independent review, verification and completion. The current security contract is [SECURITY.md](../../SECURITY.md).

The product contains no Python. The Python runtime (`src/`), its tests, `.venv` and the Python helper scripts were removed on 2026-11-16. The workspace service has only the native Rust execution host: it has no legacy ACP child, no helper scripts, and no `CORTEX_WORKSPACE_NATIVE=0` emergency opt-out. Build, packaging and setup tooling is Rust (`cortex-xtask`, `cortex-paseo-tools`).

## Crates

- `crates/cortex-core`: the Rust store domain and engine-independent core: one SQLite store per logical project and channel (reusable connections, transaction/outbox primitives, verified format-11 to format-12 migration and offline restore), lifecycle, scheduler, routing, recovery context, workspace edits and file-backed draft/report/pipeline publication with request receipts and crash intents. See [storage](storage.md#rust-core-storage-domain).
- `crates/cortex-engine`: outgoing engine sessions, the brokered MCP gateway, permission policy, tool schema catalogue (`schema::catalogue`), and the `cortex-mcp-relay` relay.
- `crates/workspace-service`: the window-independent native execution host (`native_*` modules, `incoming`), configuration readers and the owner/maintenance machine tools.
- `crates/workspace-protocol`: the Workspace wire contract; its schema is `crates/workspace-protocol/schema/workspace.json`.
- `crates/workspace-remote`: embedded remote access over `iroh` (host and client halves, pairing links, paired-device registry, tunnel); the host runs inside the Workspace service and is off by default. `crates/workspace-service/src/remote.rs` and `remote_policy.rs` hold its owner-only methods and the closed allowlist of what a paired device may call.
- `crates/workspace-client`: the machine-service bridge and request allowlist shared by the desktop shell and the Android app (`apps/cortex-workspace-android`).
- `crates/cortex-acp`: the ACP stdio ingress (`cortex-acp`).
- `crates/cortex-paseo-tools`: the Paseo store readers, Settings, setup and dev tooling (`scripts/cortex-paseo-tools.sh`).
- `crates/cortex-xtask`: generators, package stamp, pins check, bounded test runner, build driver and the installed real-input gate (`scripts/cortex-xtask.sh`).

## Native host

Workspace sprint planning is a separate description-only engine turn, not a
Core task execution. It bounds the collected reply and shares one corrective
pass between oversized and invalid replies. See [Sprint planning limits](../cortex-workspace/local-task-execution.md#sprint-planning-limits).

The desktop service selects the Rust Core for native-owned projects. It hosts one reusable, read-only Core projection provider per opened logical project/channel for desktop task pages, detail/state and filtered history. `native.query` reads those projections directly; a committed-outbox tail feeds the Core EventStream and the native desktop subscription. Small task upserts/removals update the UI without rereading the task list. The same service retains a reusable native draft writer and acquires a cooperative Core owner lease before starting a project controller. Plain `tasks.create` writes go directly to Core; attachment-bearing creates, legacy decisions, results, configuration and unsupported execution controls refuse or use their existing adapters.

`workspace-service::native_sessions` composes Core-owned channels, outgoing coordinator/worker sessions, the MCP broker and the default-deny permission policy. Worker questions, informational coordinator answers, validated plan intake and execution/review inline report/results are implemented in its narrowed catalogue. Publication runs on the owned writer lane with a durable full-payload binding; report file integrity is observed before the result/event/receipt transaction. The host embeds generated canonical coordinator/worker instructions and role-scoped skill/reference data (see `crates/cortex-xtask` `generate-instructions`); its Codex supplement is derived from the served tool schemas. The trusted `bind_workspace` hook binds an existing native task/epoch to a saved desktop draft and logical display session atomically. Public ACP messages and minimal tool activity use that session's existing history/outbox path, with real child attempt/session checks and no thoughts or raw tool inputs/outputs; a tool call keeps its kind, locations and a bounded, credential-redacted selection of its input (path, command, query, skill or report reference, and a non-private edit's text and diff).

The host's advance driver claims nodes, adds mandatory independent review on observed changes, consumes fix/replan verdicts, runs bounded read-only verification argv and applies Core's completion invariants. Fresh Git/index/file observations bind review and verification; model digests/pass flags cannot certify work. Native permission asks are cancelled with a retained diagnostic. The route/model is confirmed against observed ACP options, not inferred from chat. Atomic admission commits the draft binding, runtime task/epoch, saved input, receipt and outbox before provisioning; exact retries do not replay effects. A draft's saved model/effort/mode/language settings are qualified through the same per-task route as its coordinator turns before admission; an unavailable model or unsupported effort refuses with its own code before any effect. Native creation-time attachments and worktrees are unavailable on the native host and refuse (a documented limit).

Native-owned desktop controls enter the same host through the service handlers. A per-project control lane serializes receipt admission, task-local pump interruption, observed process settlement and fresh continuation. Stop is resumable Pause; Resume continues the retained task where it was paused (preserved questions and worker waits stay answerable; interrupted work resumes through lost-worker retry or coordinator recovery) and never replans. Explicit Retry, and a message to a task that waits for the owner, is held or was reopened, replan with a fresh coordinator after settlement; a message to a working task settles and interrupts nothing and reaches the coordinator at its next boundary (`cortex_core::lifecycle::steering`). An admitted control that never reaches its finish receipt is closed as an explicit unknown outcome (`native_control_outcome_unknown`, bound to the task revision) that Retry clears and that later restarts do not raise again. Question answers continue the bound waiting worker. Confirmed owner resolution closes without certifying unfinished work. Worker guidance uses an eight-entry assignment-local queue, a confirmed ACP cancel/reply boundary and the same worker session; worker stop revokes only its assignment. Verifier commands retain owned cancellation handles, start/finish events and exact references; owner reruns use stored argv, current result identity/digest and the same sandbox, and a separate command-stop lane stays responsive during a rerun. Service restart resumes settled checkpoints through the same driver; unsettled session/control/verification effects retain unknown-outcome blockers without replay, while paused state and questions/waits are preserved. Native executors share a process-lifetime scheduler fence with the incoming ACP host.

Complete report/tool coverage, production route/instruction qualification, permissions and live ACP session reattachment remain incomplete; offline executable/configuration qualification is not live account evidence. Projects whose stores were last written by the former Python runtime are not adopted automatically: an incoming session refuses them (`legacy_project_requires_retained_adapter`), and workspace recovery can explicitly adopt legacy tasks (see [native recovery](../cortex-workspace/local-task-execution.md#legacy-task-adoption)). Do not run two independent mutable owners over a project/channel.

## Incoming Rust ACP adapter

`crates/cortex-acp` is the ACP-v1 stdio ingress. Its transport delegates task effects to `workspace-service::incoming::IncomingHost`, which composes the native Runtime/NativeHost/Core/engine driver. It never opens a private Store or supplies an alternative scheduler. Existing-owner conflicts refuse clearly; daemon attachment is not implemented. Session/task admission, initial settings and public input commit with the native Start receipt. Streaming/replay read the retained public transcript; runtime completion still requires the shared driver, review and verification gates. Initial attachment admission retains private, hashed source bodies with transactional metadata before dispatch; engine prompts use the verified bytes, not base64 prose. Worker question batches commit all answers together. A separate read-only history facade loads format-12 sessions created by the former Python runtime without acquiring scheduler ownership or adopting their tasks. The compiled channel is reported in initialize metadata. The binary is the only external-client entry for Zed registration, the Paseo setup launch record and a Paseo source-root launch; see [native incoming ACP](native-incoming-acp.md) for limitations and checks.

## Current source map

- `crates/cortex-acp/src`: the ACP agent surface a client connects to (`main.rs`, `commands.rs`, `task_commands.rs`, `startup.rs`, `registry.rs`, `adapters.rs`, `automatic.rs`).
- `crates/cortex-core/src`: store, lifecycle, scheduler, routing, events, projections, recovery context, ownership and workspace modules.
- `crates/cortex-engine/src`: outgoing engine adapters (`engine.rs`, `external.rs`), the MCP gateway and broker (`gateway.rs`, `broker.rs`), permissions (`permission.rs`) and tool contracts (`schema.rs`).
- `crates/workspace-service/src`: the native host (`native_*`), incoming ACP host (`incoming*.rs`), configuration readers and machine tools.
- `agent-sources/`, `skills/`, `profiles.json`: the 23 worker profiles' sources and the bundled skills, rendered by `scripts/cortex-xtask.sh profiles write` and checked by `check-generated`.

Fresh ACP sessions durably initialize Development in the project store. The
host-side MCP broker gives a writing worker's brokered `command_run` in a Development or
Auto task host-writable mounts, with retained cwd/profile/policy receipts. Read-only roles and
automatic verification always get the read-only host profile, so their project stays read-only
(verification writes git-ignored directories in place and discards its other project writes). Engine
processes keep their existing jails. This is a
trusted-local-development boundary, not adversarial containment from Docker or
arbitrary owner code. Legacy/missing/unreadable state stays Guarded; explicit
client choices are preserved. See [access modes](../features/permissions-and-containment/index.md#access-mode-development-guarded-and-auto).

Feature behavior is described in the [feature index](../features/index.md); project-wide rules are in [conventions](conventions.md), [storage](storage.md), [security](security.md) and [verification](verification.md).

The no-paid startup smoke (`scripts/cortex-paseo-tools.sh acp-smoke`) launches the production entry point in an isolated temporary project and host configuration. It checks ACP framing without an engine call (it has no JSON-schema validator; that conformance check is reported as `skip`). Its optional `--fixture-connection` mode installs one isolated fake connection for a placeholder identity; it does not exercise a paid engine or real configuration. The Zed setup helper (`scripts/cortex-paseo-tools.sh print-client-recipes`) defaults to a dry run and requires explicit consent for a write.

A client must explicitly select or launch Cortex as its agent. Finding a `.cortex` directory does not activate orchestration. Every project has one `.cortex` store. Paid live checks run only on an explicit owner request naming `cli` or `desktop`, through the isolated dev Paseo environment and a disposable project; see [the dev Paseo guide](dev-environment.md).
