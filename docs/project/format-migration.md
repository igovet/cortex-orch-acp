# Format migration, upgrade and rollback (ACP format 12)

> Status: rewritten for the Rust store on 2026-11-16. The former Python migration tool (`scripts/cortex_migrate.py` with its `plan`, `migrate` and `rollback` actions) and its tests were removed; the behavior below is what `crates/cortex-core/src/store/migration.rs` and its tests (`crates/cortex-core/tests/migration.rs`, `migration_parity.rs`) implement. Statements without a source path are unverified until reviewed.

Each project's SQLite format migration applies to `cortex.sqlite3`, its access and connection locks, and the compatibility of the records read from that database. [Storage relocation](storage.md#where-the-database-lives-and-how-it-moves) moves eligible project-local storage to the private home state root. The older `<project>/.codex/cortex` root is detected separately.

User `routing-profiles.json` is separate from this SQLite format. Its JSON `format` is read as 1 or 2: format 1 is normalized to the format-2 shape in memory without touching the file, and the first change that writes the file keeps a private byte-identical backup of the format-1 original (`crates/workspace-service/src/config_read_model/profiles.rs`, `parse_profiles`). Any other `format` fails closed (`unsupported_profiles_format`) in the owner management API. An older runtime ignores that file but continues to read the last profile materialized into user `routing.json`. No project profile migration exists.

## Compatibility and current format

Current stores use `PRAGMA user_version=12` and the application id 1129467218. Format 12 is the ACP-only storage format: source provenance (`source_turns`, `source_resets`), task reports, orchestration state, work graph, candidates, checks and the other additive ACP tables are retained; the retired Codex-plugin hook tables (`hook_events`, `hook_pending_sources`, `hook_hints`, `hook_agent_bindings` and `hook_command_sessions`) are absent.

Format 11 is accepted only as a migration input and may contain the old hook tables. **Format 10 is not accepted**: the Rust store refuses it (and any other unknown application id or version) with `unsupported_storage`; the former Python tool's `10 -> 12` path was removed with it and has no replacement. The format-11 input includes projects written by the retired Python runtime. Format 11 upgrades to 12 automatically:

- `Store::open(.., OpenMode::Initialize)` on a format-11 database performs the verified upgrade under the exclusive access fence (`.access.lock` exclusive, `.connections.lock` exclusive for the duration), so no other process holds a connection. It first creates a **fresh** (`O_EXCL`, mode 0600, never overwritten) backup in the private `.migration-backups/` directory (`cortex.sqlite3.format11-<id>.bak`) with SQLite's backup API, so the backup is a verified logical snapshot of the committed database state including rows committed in a WAL (SQLite may serialize it with different page bytes). The backup passes `PRAGMA integrity_check` and `PRAGMA foreign_key_check` and is fsynced together with its directory, and its SHA-256 digest is computed, all before any schema change.
- It then applies the whole upgrade as **one exclusive SQLite transaction**: the current additive schema, `DROP TABLE IF EXISTS` of the five hook tables (current ACP entities are preserved), verification by `integrity_check` and `foreign_key_check` before commit, and a `format_history` row (`migrate`, 11, 12, backup path, SHA-256, time). Markdown files are never opened.
- **Genuine Python-produced format-11 shapes are supported.** The additive installer adds a missing nullable `host_transcript.message_id` (the Python producer never recorded one; existing rows get `NULL`, so no message grouping is invented) and a missing nullable `attempt_revisions.manifest_json`; where a column exists its values are untouched. The five retired hook tables are dropped from the live database and remain only in the backup. Row content (tasks, reports, editions, drafts, settings, ACP sessions, transcript) is preserved.
- **Schema shape is validated before commit.** All registered tables, optional groups and required columns are checked inside the same transaction, before `COMMIT`. An unsupported or incomplete shape therefore rolls back: the main database file is byte-unchanged and the open fails with a typed `incomplete_storage_schema` (or `partial_storage_schema`) reason instead of leaving a half-upgraded store.
- If any step before commit fails (including schema validation), the SQLite transaction rolls back and the main database is left unchanged; the backup is **not** copied over the live database on this path. Because the backup is created and verified before the transaction starts, a refusal after that point can leave the backup behind in `.migration-backups/`. The digest is computed for the `format_history` row; comparing it with an expected digest happens only in the explicit offline restore below, where a mismatch is reported as `migration_backup_invalid`. A crash before commit leaves the live database untouched (SQLite rolls back its own uncommitted transaction on the next open); a crash after commit leaves a fully upgraded, `format_history`-recorded store. No half-applied schema is ever left live and used.
- `OpenMode::InspectImmutable` (and `LiveReadOnly`) never migrate: on a format-11 database they report `legacy_storage_migration_required` and write nothing. There is no separate `plan` operation; the read-only inspection above is the supported way to see that a store needs the upgrade, and a normal writable open performs it.

Every later ACP metadata addition remains an independent, self-healing, all-or-nothing optional table group on top of format 12:

- Every normal writable `OpenMode::Initialize` open runs the complete `CREATE TABLE IF NOT EXISTS ...` schema script, so a pre-existing store simply gains whichever groups it predates, with zero rows, and no version bump is ever required for this. Non-initializing inspection opens never repair schema or backfill rows; see [storage inspection](storage.md). A nonempty WAL is refused by `InspectImmutable`, not ignored. Live runtime validation (`OpenMode::RuntimeValidate`, and `LiveReadOnly`) instead shares the access lock and reads committed WAL data, allowing SQLite sidecar housekeeping but never installing schema or migrating a legacy format.
- The optional-group layout is enumerated in `crates/cortex-core/src/store/groups.json` and `columns.json`; opening a store where a group is present only partly refuses with `partial_storage_schema`, and a table missing expected columns with `incomplete_storage_schema`.

A store file that does not exist yet is created `O_EXCL` with mode 0600; Initialize never opens an existing database with a plain descriptor, because closing it would drop the process's POSIX locks, including those of live SQLite connections, and let another process delete the live WAL/SHM and corrupt the store (see `create_private_database` in `crates/cortex-core/src/store/locks.rs`).

## Offline restore (library only)

`migration::restore` (`crates/cortex-core/src/store/migration.rs`) is the offline rollback primitive. **No shipped command exposes it**: the former `cortex_migrate rollback` CLI was removed, and the function is called only by the crate's tests. It requires `access_stopped` and `confirm` (refusing with `migration_requires_stopped_access` or `rollback_requires_confirmation`), the caller-supplied expected SHA-256 of the backup, and an owner-private backup file in an owner-private directory. It takes the same exclusive `.access.lock` and `.connections.lock`, copies the exact backup bytes to a private temporary file and verifies that the digest matches (`migration_backup_invalid` otherwise), that the application id and format (11 or 12) are accepted (`rollback_backup_incompatible` otherwise), and that integrity and project identity checks pass. It checkpoints the current database, removes stale sidecars, atomically renames the verified copy over `cortex.sqlite3` and appends one JSON line to `rollback.log`. It never touches Markdown, drafts, engine state or accounts, and it never merges or replays work done after the backup. A crash before the rename leaves the live database untouched (a stray `.rollback-*.tmp` is removed at the start of the next attempt); the rename itself is atomic.

Restoring a format-11 backup yields a project-local store that requires the
upgrade again (`legacy_storage_migration_required` for a non-initializing open).
The primitive refuses a relocated database or its checkout marker with
`relocated_store_restore_unsupported`. To return the current format-12
database and documents to the checkout, use
[`project-stores return-to-project`](storage.md#administering-home-stores).

## Opening Python-era projects through incoming ACP

Incoming `cortex-acp` opens older projects through the same fenced writable store initialization as the Workspace service (`crates/cortex-acp/src/lib.rs`, `crates/workspace-service/src/incoming.rs`):

- **Format 11:** `session/new` reaches the writable `Initialize` open, which performs the verified upgrade above (private backup, validation before commit; a failure rolls back and leaves the main database unchanged; a migration that fails schema validation does not copy the private backup back over the main database, and the backup may remain). `session/load` of a format-11 project migrates only when a lock-protected read probe finds the exact session ID, project root and a persisted Rust-session marker; a Python-created or unknown session ID does not trigger migration and the project is left unchanged.
- **Python-era tasks:** a project that still contains tasks last written by the Python runtime is no longer refused. It opens through the shared fenced recovery/adoption (scheduler and Core lifetime fences, a separate host-transfer event, epoch advance, old channels revoked). Unsettled effects, legacy command/check starts and claimed answer deliveries stay unknown and are **not replayed**; a terminal result remains readable. Continuing an old task from incoming ACP is intentionally not supported (a product decision): new work starts as a new task in a new chat.
- **Old ACP sessions:** a session created by the Python runtime replays its history on `session/load` but stays read-only history. A prompt or other writable operation in it is refused with JSON-RPC code `-32602` and `error.data.reason = legacy_session_read_only`; the message says the chat was created by an earlier Cortex version, is read-only history and no longer supports new work, and tells the owner to open a new chat and create a new task there. The refusal appends nothing, does not promote the session, creates no task and calls no engine.
- **Project already registered under another ID:** if the project root is already registered (for example by an earlier Workspace version) under a different project ID, incoming ACP resolves that record by canonical root and the authenticated local user and reuses it; no duplicate row is created and no client-supplied ID is trusted. A record for the same root owned by a different user, or an ID collision with another root, is still refused with `project_context_conflict`.
- **Refusals are explained.** Storage failures carry a human-readable `message` plus a stable `reason` (and `retryable`) in the JSON-RPC error `data`; Core exposes the same pair as `CoreError::storage_diagnostic()` (`crates/cortex-core/src/store/diagnostic.rs`). Stable reasons: `unsupported_storage` (format 10 gets its own text: a retired Python format this release cannot open or upgrade; keep the original files and use a matching historical release on a copy or a verified backup; other unknown formats get a separate text), `legacy_storage_migration_required` (non-initializing open of format 11), `legacy_storage_root_detected`, `partial_storage_schema`, `incomplete_storage_schema`, `project_storage_mismatch` (the database belongs to a different project path) and `busy` (the only retryable one). A non-initializing open that refuses format 11, or an open that refuses an unknown format, does not migrate the store or create a migration backup. A format-11 upgrade refused by schema validation rolls back without rewriting the main database, but the backup created just before it may remain.
- **Legacy root `.codex/cortex`:** Before creating a fresh release store, the runtime checks this older layout by names and metadata and reports `legacy_storage_root_detected`. This guard does not open or relocate that layout. Workspace Dev never inspects it.

## Python-era fixture tests

The real historical samples live in `tests/fixtures/python-era/` (format 11 and format 12 projects and routing profiles 1 and 2, all written by the Python runtime's own code; producer revisions, identity and SHA-256 list in its `PROVENANCE.md`). Tests need no Python and no network and run on pristine copies under a private temp root at the recorded project path: `crates/cortex-core/tests/migration.rs` (`genuine_python_format11_migrates_without_losing_data`, `unsupported_format11_shape_rolls_back_without_rewriting_main_database`) and the `python-era` cases of `crates/cortex-acp/tests/incoming.rs` (helpers in `tests/support/python_era.rs`). They cover Store and incoming-ACP opens of formats 11 and 12, data parity against `expected.json`, read-only old sessions, a working new session, format-10/unknown refusals, wrong-root and legacy-root cases. Incoming ACP cases run on the Dev channel; Release-only refusals are checked at the Store level.

## Concurrency

The upgrade and the restore both take the storage directory's `.access.lock` exclusively; every live ACP/MCP operation takes it shared. Two mutating operations (a second upgrade, a restore, or an old runtime against the new one) can never proceed against the same project at once; the second is refused as busy. The Rust tests (`migration.rs`, `migration_parity.rs`, `sqlite_locks.rs`) exercise the verified backup, the rollback on injected failure, the crash points (before backup, after backup, before commit, after commit; a unit-test-only crash hook) and the refusal while a connection is open.

## What is explicitly not supported

- No downgrade-read of data written by a newer format than this runtime build recognizes: refused, never attempted.
- No migration of format 10 or of an unknown application id.
- No rollback to the legacy Codex-plugin-harness runtime (gateway, hooks, `marketplace_bootstrap`, `.codex-plugin` marketplace wiring): that runtime was removed with no supported path back to it, and there is no legacy-comparison/rollback operation at all, by explicit product decision.
- No command-line `plan`, `migrate` or `rollback`; no separate backup path option. The backup location is always the store's private `.migration-backups/` directory.
