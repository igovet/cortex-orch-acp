# Format migration, upgrade and rollback (ACP format 12)

> Status: rewritten for the Rust store on 2026-11-16. The former Python migration tool (`scripts/cortex_migrate.py` with its `plan`, `migrate` and `rollback` actions) and its tests were removed; the behavior below is what `crates/cortex-core/src/store/migration.rs` and its tests (`crates/cortex-core/tests/migration.rs`, `migration_parity.rs`) implement. Statements without a source path are unverified until reviewed.

This page covers offline SQLite format-version safety for one project's own store: `cortex.sqlite3` (under `.cortex`, or `.cortex-dev` for Workspace Dev), its `.access.lock` and `.connections.lock`, and the Markdown task/draft trees living alongside it. It does **not** cover the already-completed legacy-root move (`<project>/.codex/cortex` to `<project>/.cortex`), and it is not a rollback to the retired Codex plugin harness.

User `routing-profiles.json` is separate from this SQLite format. Its JSON `format` is 1; an unknown format fails closed in the owner management API. An older runtime ignores that file but continues to read the last profile materialized into user `routing.json`. No project profile migration exists.

## Compatibility and current format

Current stores use `PRAGMA user_version=12` and the application id 1129467218. Format 12 is the ACP-only storage format: source provenance (`source_turns`, `source_resets`), task reports, orchestration state, work graph, candidates, checks and the other additive ACP tables are retained; the retired Codex-plugin hook tables (`hook_events`, `hook_pending_sources`, `hook_hints`, `hook_agent_bindings` and `hook_command_sessions`) are absent.

Format 11 is accepted only as a migration input and may contain the old hook tables. **Format 10 is not accepted**: the Rust store refuses it (and any other unknown application id or version) with `unsupported_storage`; the former Python tool's `10 -> 12` path was removed with it and has no replacement. Format 11 upgrades to 12 automatically:

- `Store::open(.., OpenMode::Initialize)` on a format-11 database performs the verified upgrade under the exclusive access fence (`.access.lock` exclusive, `.connections.lock` exclusive for the duration), so no other process holds a connection. It first creates a **fresh** (`O_EXCL`, mode 0600, never overwritten) backup in the private `.migration-backups/` directory (`cortex.sqlite3.format11-<id>.bak`) with SQLite's backup API, so the backup is a verified logical snapshot of the committed database state including rows committed in a WAL (SQLite may serialize it with different page bytes). The backup passes `PRAGMA integrity_check` and `PRAGMA foreign_key_check` and is fsynced together with its directory, and its SHA-256 digest is computed, all before any schema change.
- It then applies the whole upgrade as **one exclusive SQLite transaction**: the current additive schema, `DROP TABLE IF EXISTS` of the five hook tables (current ACP entities are preserved), verification by `integrity_check` and `foreign_key_check` before commit, and a `format_history` row (`migrate`, 11, 12, backup path, SHA-256, time). Markdown files are never opened.
- If any step before commit fails, the transaction rolls back and the verified backup snapshot is restored into the live connection; a failure to verify the backup digest is reported as `migration_backup_invalid`. A crash before commit leaves the live database untouched (SQLite rolls back its own uncommitted transaction on the next open); a crash after commit leaves a fully upgraded, `format_history`-recorded store. No half-applied schema is ever left live and used.
- `OpenMode::InspectImmutable` (and `LiveReadOnly`) never migrate: on a format-11 database they report `legacy_storage_migration_required` and write nothing. There is no separate `plan` operation; the read-only inspection above is the supported way to see that a store needs the upgrade, and a normal writable open performs it.

Every later ACP metadata addition remains an independent, self-healing, all-or-nothing optional table group on top of format 12:

- Every normal writable `OpenMode::Initialize` open runs the complete `CREATE TABLE IF NOT EXISTS ...` schema script, so a pre-existing store simply gains whichever groups it predates, with zero rows, and no version bump is ever required for this. Non-initializing inspection opens never repair schema or backfill rows; see [storage inspection](storage.md). A nonempty WAL is refused by `InspectImmutable`, not ignored. Live runtime validation (`OpenMode::RuntimeValidate`, and `LiveReadOnly`) instead shares the access lock and reads committed WAL data, allowing SQLite sidecar housekeeping but never installing schema or migrating a legacy format.
- The optional-group layout is enumerated in `crates/cortex-core/src/store/groups.json` and `columns.json`; opening a store where a group is present only partly refuses with `partial_storage_schema`, and a table missing expected columns with `incomplete_storage_schema`.

A store file that does not exist yet is created `O_EXCL` with mode 0600; Initialize never opens an existing database with a plain descriptor, because closing it would drop the process's POSIX locks, including those of live SQLite connections, and let another process delete the live WAL/SHM and corrupt the store (see `create_private_database` in `crates/cortex-core/src/store/locks.rs`).

## Offline restore (library only)

`migration::restore` (`crates/cortex-core/src/store/migration.rs`) is the offline rollback primitive. **No shipped command exposes it**: the former `cortex_migrate rollback` CLI was removed, and the function is called only by the crate's tests. It requires `access_stopped` and `confirm` (refusing with `migration_requires_stopped_access` or `rollback_requires_confirmation`), the caller-supplied expected SHA-256 of the backup, and an owner-private backup file in an owner-private directory. It takes the same exclusive `.access.lock` and `.connections.lock`, copies the exact backup bytes to a private temporary file and verifies that the digest matches (`migration_backup_invalid` otherwise), that the application id and format (11 or 12) are accepted (`rollback_backup_incompatible` otherwise), and that integrity and project identity checks pass. It checkpoints the current database, removes stale sidecars, atomically renames the verified copy over `cortex.sqlite3` and appends one JSON line to `rollback.log`. It never touches Markdown, drafts, engine state or accounts, and it never merges or replays work done after the backup. A crash before the rename leaves the live database untouched (a stray `.rollback-*.tmp` is removed at the start of the next attempt); the rename itself is atomic.

Restoring a format-11 backup yields a store this runtime refuses to open for writing without re-running the upgrade (`legacy_storage_migration_required` for a non-initializing open): restore is for returning to the state a matching **older** Cortex build can read, not for making this runtime read an older format. No downgrade-read path is provided.

## Concurrency

The upgrade and the restore both take the storage directory's `.access.lock` exclusively; every live ACP/MCP operation takes it shared. Two mutating operations (a second upgrade, a restore, or an old runtime against the new one) can never proceed against the same project at once; the second is refused as busy. The Rust tests (`migration.rs`, `migration_parity.rs`, `sqlite_locks.rs`) exercise the verified backup, the rollback on injected failure, the crash points (before backup, after backup, before commit, after commit; a unit-test-only crash hook) and the refusal while a connection is open.

## What is explicitly not supported

- No downgrade-read of data written by a newer format than this runtime build recognizes: refused, never attempted.
- No migration of format 10 or of an unknown application id.
- No rollback to the legacy Codex-plugin-harness runtime (gateway, hooks, `marketplace_bootstrap`, `.codex-plugin` marketplace wiring): that runtime was removed with no supported path back to it, and there is no legacy-comparison/rollback operation at all, by explicit product decision.
- No command-line `plan`, `migrate` or `rollback`; no separate backup path option. The backup location is always the store's private `.migration-backups/` directory.
