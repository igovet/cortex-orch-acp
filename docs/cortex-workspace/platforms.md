# Platform policy

**Status: planned product policy. The Ubuntu desktop local slice (M2) is built with the checks recorded below; no platform is qualified for release.**

First release: Ubuntu execution machine and desktop client. The Android remote client is deferred by the owner's decision of 2026-11-05 and is gated by Gate M. Android requires a physical-device qualification, including keyboard, lifecycle, networks and push. Linux WebKitGTK GPU/session behavior must be measured on representative hardware. macOS and Windows are later targets with separate packaging, runtime, security and test qualification; iOS is only a possible future target. A cross-platform shell does not imply local Cortex runtime support. No platform is currently qualified for this planned product.

## Desktop build prerequisites (observed 2026-11-05)

Native builds run in a Docker container, not on the host (owner decision of 2026-11-05). The host needs no development packages, and the owner does not install system libraries for the build. The host needs Docker usable by the invoking user without sudo, and a user-level Rust installation for host-side tooling (pin validation, contract checks and the Python tests).

### Builder image

`packaging/container/Dockerfile` builds on an Ubuntu 26.04 base pinned by digest. The image installs the native development packages `libwebkit2gtk-4.1-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev` and `libxdo-dev`; they are not installed on the host. `scripts/build_workspace_desktop.py` runs `packaging/container/build.sh` with the repository snapshot and no host credentials. Its dev channel is the default; `--test-workspace` also runs `cargo test --locked --workspace` inside the container. The produced `.deb` derives its versioned runtime library dependencies from the compiled binaries; it does not depend on any development package. A `.deb` built on a newer Ubuntu base can raise the minimum runtime baseline for older Ubuntu releases; this host is not evidence of compatibility with them.

### Per-project channel stores

Workspace Dev opens `<project>/.cortex-dev/cortex.sqlite3`, its reports and drafts beside it. Default/release ACP continues to use `<project>/.cortex/cortex.sqlite3`. An existing release store is not a folder-opening error. Dev never opens, imports or migrates it; linked worktrees share one logical-project store within their channel. Registration creates the private `.cortex-dev` directory and its `.cortex-dev/owner.json` reservation together, binding its device/inode before any database opens. Existing validated root `.cortex-dev-owner.json` reservations migrate once to this location. Recognized private `.cortex-workspace-dev.json` markers move to `.cortex-dev/legacy-workspace.json`; unknown, linked or foreign files stay untouched. No old `.cortex` database is opened or imported. An activated older project with no dev store gets a fresh reservation on restart; an existing unreserved/replaced store stays refused. Saved materialized sprint plans restore missing task drafts with their original member identities and dependency order, without importing old runtime history. The queue pauses for review; existing and explicitly purged tasks are not replaced. Ambiguous plans remain paused rather than guessed. See [channel contract](backlog/CW-S12.md).

### Debian build ordering and reproducibility

The archive control Version and filename use `1.0.6+z<YYYYMMDDhhmmssffffff>.sha256.<16-hex-content-hash>`. The `z` is intentional: Debian sorts it after `s`, so every new-format version sorts above every old `1.0.6+sha256.*` version, including `f3eee9da173725e1` and `ffffffffffffffff`. A numeric stamp directly after `+` would **not** provide that migration ordering. Within the new format, the UTC microsecond stamp decides before the hash. Explicit owner-run `scripts/build-prod-deb.sh` builds the production channel locally with authorization `local-owner-test`; its archive version adds `.local`, refused by the unchanged GitHub publisher. The official clean-main path retains `github-main-clean` and its existing version format. The embedded readable `/usr/share/<package>/package-identity.json` stays unchanged, as does the runtime identity.

The builder reserves an explicit stamp before container execution, passes only that value to the packager, and records it in `build-stamp.txt` and `manifest.json` under the build output. The packager never reads the clock. Default invocations, including `--resume` cache reuse, allocate an increasing stamp under a local file lock in `.workspace-build/last-build-stamp.txt`; a repeated or backward clock advances the previous value by one microsecond. Failed builds can consume stamps. Keep that state for local ordering. Separate build roots/machines must supply globally increasing `--build-stamp` inputs; there is no cross-machine allocator. The manual release workflow serializes each branch independently and uses the same builder: `main` publishes `v<debian-version>` as Latest; `dev` publishes `dev-v<debian-version>` as a prerelease excluded from Latest. Dev installs manually and has no in-app updates. Tags include the actual ordered Debian version, not only the runtime content identity.

For a reproducible packaging replay with identical sources, dependencies and binaries, pass the recorded stamp explicitly, for example `python3 -B scripts/build_workspace_desktop.py --resume build-abcdefgh --build-stamp 20261106060000000000`. This deliberately reuses a version, not a new upgrade. An explicit new stamp at or below the retained allocator value is refused; matching the selected cache's saved stamp permits replay. Debian archive timestamps remain normalized, and identical inputs retain byte-identical packaging. The owner still uses one ordinary `sudo apt install ./<new-archive>.deb` command, without a downgrade flag.

### Self-contained package startup

Both channels include every stamped ACP payload file plus the Workspace host under `/usr/lib/<package>/runtime`. Archive file modes are normalized for normal-user reads, and Debian timestamps are fixed for reproducible packaging. The unit uses absolute paths and ignores old `service.env` files. No checkout or settings clone is needed. The package ships a `default.target.wants` link for login startup; first desktop launch in an existing session runs bounded native `/usr/bin/systemctl --user daemon-reload` and `start` calls for its own unit. Retry reconstructs a previously unavailable bridge and retries connection, never a submitted mutation. Upgrades reload and try-restart matching active user units best effort; removal stops them without deleting user data. There is no linger or boot-survival promise.

The Cortex logo is the window icon (`bundle.icon` in `tauri.conf.json`, compiled in) and the launcher icon: each package ships it under `usr/share/icons/hicolor` at 32 to 512 pixels, named after the package, and its `.desktop` entry carries `Icon=` and `StartupWMClass=<identifier>`. GTK takes the Wayland app id from the identifier, so GNOME matches a running window to the entry by that key; on X11 it matches by the binary name. Pre-sized PNGs live in `packaging/icons`, and the 512 pixel one is `assets/logo.png` byte for byte.

Runtime dependencies include Python 3.11+, Git, CA certificates, bubblewrap, systemd and the user session bus, plus libraries derived from the native ELF binaries. Nodejs and npm are not apt dependencies. Both channels include a checksum-verified Node 24.14.1 and locked Codex/Claude adapters and dependencies under `/usr/lib/<package>/engines`. Discovery prefers that read-only tree and its own Node; no first-run adapter download is needed. It does not scan shell-specific version managers or reuse production adapters in dev. Native Codex/Claude login directories stay in the real HOME and are never copied. First activation runs existing absent-only defaults and background connection setup; missing login and discovery failures are shown separately from service connectivity.

`python3 -B scripts/build_workspace_desktop.py --check-install` adds the no-paid clean Ubuntu container smoke. It installs the archive through apt without build tools or a checkout, checks normal-user bundled-runtime activation, ignores a deliberately stale environment file, preserves the project store on removal and upgrades a legacy two-binary archive shape. Bundled adapters and synthetic login markers exercise real discovery and registration; model refresh is stubbed, so this does not qualify a model workload. The separate `packaging/container/check_bundled_engines.py --archive <package.deb>` check installs with `--network none`, launches each real adapter through Cortex up to ACP initialize, and checks native versions without a prompt.

The basic install smoke still cannot host a user manager. A separate explicitly authorized check on 2026-11-06 (`packaging/container/check_systemd.py`) passed with real systemd as PID 1 and a lingering disposable user: clean install, startup through the shipped `default.target.wants` link, desktop-driven start in a running session, active-unit reinstall/restart, removal/stop, and replacement of the exact earlier `1.0.6+sha256.f3eee9da173725e1` archive. It uses a privileged disposable container with a private cgroup namespace, not a host service, and mounts no host bus, cgroups, home or credentials. This is lifecycle evidence, not hostile-code isolation or a boot-survival promise.

The earlier namespace failures were context-dependent: the worker command ran under enforcing `bwrap//&unpriv_bwrap` and could not create another user namespace. The authorized host-direct probe under `Paseo (unconfined)` passed while `apparmor_restrict_unprivileged_userns=1` and `unprivileged_userns_clone=1`. All ten focused real MCP discovery and runtime sandbox tests passed there, including real tool listing, deadline handling and write/private-store refusal. These use disposable fixtures, not a production task. No host policy was changed and no package AppArmor profile or privileged helper was needed for that observed host route; other distributions and confinement contexts remain unqualified.

### Host-direct native builds are not a supported route

A direct host Cargo build of the native desktop crate fails on missing development metadata (`pkg-config` cannot find `webkit2gtk-4.1`). That failure is retained as a failed observation, not as a pass. Do not install the development packages on the host to make it pass; use the container route.
