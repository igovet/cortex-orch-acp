# Platform policy

**Status: platform policy. The Ubuntu desktop is implemented and checked in containers with the checks recorded below (no-paid; fake engines). Not verified: a real Ubuntu desktop session and GPU, the different-OS-user connection, paid live runs and a published release. Android has an app (`apps/cortex-workspace-android/`) and a build script, built once as a debug APK on the development machine; it is not verified on a physical device or emulator. macOS and Windows are not implemented. No platform is qualified for release.**

First release: Ubuntu execution machine and desktop client. The Android remote client follows the desktop: the owner approved its static mockups and design decisions on 2026-11-17 ([mobile approval](design/mobile-approval.md)), and it is built as the shared interface in a Tauri 2 Android app. It has no local machine and connects only to paired remote machines. Android requires a physical-device qualification, including keyboard, lifecycle, networks and push. Linux WebKitGTK GPU/session behavior must be measured on representative hardware. macOS and Windows are later targets with separate packaging, runtime, security and test qualification; iOS is only a possible future target. A cross-platform shell does not imply local Cortex runtime support. No platform is currently qualified.

### Debian build ordering and reproducibility

The archive control Version and filename use `1.0.6+z<YYYYMMDDhhmmssffffff>.sha256.<16-hex-content-hash>`. The `z` is intentional: Debian sorts it after `s`, so every new-format version sorts above every old `1.0.6+sha256.*` version, including `f3eee9da173725e1` and `ffffffffffffffff`. A numeric stamp directly after `+` would **not** provide that migration ordering. Within the new format, the UTC microsecond stamp decides before the hash. Explicit owner-run `scripts/build-prod-deb.sh` builds the production channel locally with authorization `local-owner-test`; its archive version adds `.local`, refused by the unchanged GitHub publisher. The official clean-main path retains `github-main-clean` and its existing version format. The embedded readable `/usr/share/<package>/package-identity.json` stays unchanged, as does the runtime identity.

The builder reserves an explicit stamp before container execution, passes only that value to the packager, and records it in `build-stamp.txt` and `manifest.json` under the build output. The packager never reads the clock. Default invocations, including `--resume` cache reuse, allocate an increasing stamp under a local file lock in `.workspace-build/last-build-stamp.txt`; a repeated or backward clock advances the previous value by one microsecond. Failed builds can consume stamps. Keep that state for local ordering. Separate build roots/machines must supply globally increasing `--build-stamp` inputs; there is no cross-machine allocator. The manual release workflow serializes each branch independently and uses the same builder: `main` publishes `v<debian-version>` as Latest; `dev` publishes `dev-v<debian-version>` as a prerelease excluded from Latest. Dev installs manually and has no in-app updates. Tags include the actual ordered Debian version, not only the runtime content identity.

For a reproducible packaging replay with identical sources, dependencies and binaries, pass the recorded stamp explicitly, for example `scripts/cortex-xtask.sh build-deb --resume build-abcdefgh --build-stamp 20261106060000000000`. This deliberately reuses a version, not a new upgrade. An explicit new stamp at or below the retained allocator value is refused; matching the selected cache's saved stamp permits replay. Debian archive timestamps remain normalized, and identical inputs retain byte-identical packaging. The owner still uses one ordinary `sudo apt install ./<new-archive>.deb` command, without a downgrade flag.

### Self-contained package startup

Both channels include every stamped payload file (no Python and no `src/`) plus the Workspace host under `/usr/lib/<package>/runtime`. Archive file modes are normalized for normal-user reads, and Debian timestamps are fixed for reproducible packaging. The unit uses absolute paths and ignores old `service.env` files. No checkout or settings clone is needed. The package ships a `default.target.wants` link for login startup; first desktop launch in an existing session runs bounded native `/usr/bin/systemctl --user daemon-reload` and `start` calls for its own unit. Retry reconstructs a previously unavailable bridge and retries connection, never a submitted mutation. Upgrades reload and try-restart matching active user units best effort; removal stops them without deleting user data. There is no linger or boot-survival promise.

The Cortex logo is the window icon (`bundle.icon` in `tauri.conf.json`, compiled in) and the launcher icon: each package ships it under `usr/share/icons/hicolor` at 32 to 512 pixels, named after the package, and its `.desktop` entry carries `Icon=` and `StartupWMClass=<identifier>`. GTK takes the Wayland app id from the identifier, so GNOME matches a running window to the entry by that key; on X11 it matches by the binary name. Pre-sized PNGs live in `packaging/icons`, and the 512 pixel one is `assets/logo.png` byte for byte.

Runtime dependencies include Git, CA certificates, systemd and the user session bus (no bubblewrap: confined commands and contained MCP servers use the kernel's Landlock), plus libraries derived from the native ELF binaries. Nodejs and npm are not apt dependencies. Both channels include a checksum-verified Node 24.14.1 and locked Codex/Claude adapters and dependencies under `/usr/lib/<package>/engines`. Discovery prefers that read-only tree and its own Node; no first-run adapter download is needed. It does not scan shell-specific version managers or reuse production adapters in dev. Native Codex/Claude login directories stay in the real HOME and are never copied. First activation runs existing absent-only defaults and background connection setup; missing login and discovery failures are shown separately from service connectivity.

## Desktop notifications on GNOME and Wayland

The machine service raises the notifications (`crates/workspace-service/src/notifier.rs`), so they arrive while no window is open. It works out the owner moments of one project when that project's runtime or owner state changes (the same events the open windows receive). The one timer is the no-progress check: every five minutes a light read of each active project's working tasks (`native_progress.rs`) rereads a project only when a no-progress notification fell due or went away. Each notification goes to `org.freedesktop.Notifications` on the owner's session bus with the hint `desktop-entry=<package>` (the installed `/usr/share/applications/<package>.desktop`) and the default action. The service holds that one bus connection and listens on it for `ActivationToken`, `ActionInvoked` and `NotificationClosed`. No D-Bus library is in the locked dependency set apart from GIO, which belongs to the GTK stack the service does not link, so `crates/workspace-service/src/session_bus.rs` speaks the few calls it needs over the bus socket (EXTERNAL authentication, `Hello`, `AddMatch`, `Notify`, `CloseNotification`). The service needs no display server. Without a session bus (a headless machine, no desktop session) it raises nothing and `service.status` reports `notifications.state` as `no_session_bus` or `session_bus_unreachable`; with one it reports `raising`.

What GNOME Shell 50.1 does, read from its installed `notificationDaemon.js` (the `org.gnome.Shell.Notifications` service and the shell's own daemon): it finds the app by the sender's window, else by `desktop-entry`, so the service's notifications carry the app's name and icon; a click on a notification with a default action emits `ActivationToken(id, token)` and then `ActionInvoked(id, "default")`, delivered only to the connection that sent that notification, and does not itself launch or activate the app; when that connection leaves the bus, the shell removes the app's notifications.

- **A window is open (on another tab, minimized or behind other windows).** The service sends the click's target to the open windows as the `notification_open` service event. The desktop shell checks the target's exact shape (`policy::notification_target`) and claims the click with `notifications.opened`, which hands it the activation token. The token is spent by the process that raises its window, so it travels to the window rather than being used by the service. On Wayland the window gives the token to GTK (`gdk_wayland_display_set_startup_notification_id`) before `gtk_window_present`, which GTK spends on its xdg-activation request, so Mutter's focus-stealing prevention lets the window take focus; on X11 the token is the window's startup id. Without a token the compositor may only mark the window as wanting attention; the place still opens.
- **No window is open.** If no window claims the click within two seconds, the service starts the app through the user manager, `systemd-run --user --collect --quiet --no-block --setenv=DESKTOP_STARTUP_ID=<token> --setenv=XDG_ACTIVATION_TOKEN=<token> -- /usr/bin/<desktop binary>` (the desktop entry's own `Exec`), so it runs with the graphical session's environment rather than the service's. GTK 3 reads `DESKTOP_STARTUP_ID` at start and spends it on the first window; `XDG_ACTIVATION_TOKEN` is set for toolkits that read that name. The service keeps the target in memory, and the new window collects it once with `notifications.take` (used once, kept for one minute) and opens it.
- **What the window tells the service.** The focused desktop window reports the task or sprint on view and the kinds the owner wants (`notifications.report`, on every change and every minute while it keeps focus; a report holds 90 seconds). Nothing is raised for that place, and one already out for it is withdrawn. A service that answers `raising: false`, or a service without these methods, leaves the window's own question notifications, sent from the window's process the same way.
- **Limits.**
  - The app is not single-instance: with two windows open, each claims a click it receives and the first claim wins, so only one raises itself, but both may open the place.
  - The two-second wait applies only when no window is open; a window that has stopped answering without closing delays the start by those two seconds.
  - A focus report from a window that ended without closing (killed or crashed) keeps holding back that one place for up to 90 seconds.
  - The service's own pending targets live only in memory: a service restart between the click and the window's start loses that one target, and the window opens on its last tabs.
  - A paired phone never sees a desktop click: the desktop's `notifications.report`, `.opened` and `.take` are outside the remote allowlist, and the phone's bridge drops `notification_open`; a phone app built before this change reconnects its subscription once per click, because it does not know the event. The phone raises its own notifications from the same moments instead ([Android phone notifications](#android-phone-notifications)).
  - Notifications of a stopped service are withdrawn as it stops; one killed without stopping cannot withdraw them, and GNOME removes them when its bus connection goes.
- **Verified.** No-paid unit tests cover the mapping from runtime and owner state to kinds and targets, replacement and withdrawal, the focus and kind rules, the claim and the one-minute pending target, the report and request shapes and the launch command. On a private `dbus-daemon` (never the owner's session bus), a stand-in notification server answers the service client's `Notify`, sends `ActivationToken` and `ActionInvoked` to the sender only, and receives `CloseNotification`; the service's book returns the target with its token, and an id it did not raise opens nothing. In the builder container under `dbus-run-session`, the window's own path makes the same round trip through GIO. Not verified: the real GNOME Shell, focus through a real xdg-activation token in either process, `systemd-run` starting the installed app in a real session, and the click reaching the rendered window. The rendered and installed gates run Mutter without GNOME Shell, so they have no notification server and no source of real activation tokens.

## Android phone notifications

The phone raises its own notifications; no push service is used. The machine service works out the owner moments of each active project as above (`notifier::items` and the no-progress check), and since this change it does so with or without a session bus: without one it only raises nothing locally. Each read also updates one snapshot of every project's moments for paired phones. A phone subscribes with `notifications.subscribe` (exactly `{}`, the one `notifications.*` method in the remote allowlist, `remote_policy.rs`) on its own tunnelled stream; the service answers `{"subscribed":true}`, sends the snapshot as a `notification_moments` service event at once and again after each change, and ends the stream when the phone sends anything or closes it. A moment is `{kind, fingerprint, title, target}`: the kind (`question`, `stop`, `access`, `planning`, `result`, `failed`, `paused`, `stalled`), the first 32 hex digits of the SHA-256 of the moment's state, the title (at most 120 characters) and the desktop's closed target. A snapshot carries at most 200 moments. The desktop's own kinds and focus settings do not filter it.

- **Phone side** (`apps/cortex-workspace-android/src-tauri/src/moments.rs`, `phone.rs`). While notifications are on, the phone keeps one moments subscription per paired machine, not only the open one: a lost one is retried after 2 seconds, doubling to at most 60 seconds, and one a machine refuses (an older machine service) every 5 minutes. Every moment is checked (`policy::notification_target`, kind list, fingerprint shape, title bound) and invalid ones are dropped. A fingerprint not announced before raises one notification per task or sprint of that machine on the channel of its kind: Needs your answer (question, stop, access, planning), Results ready (result), Failures (failed, paused, stalled); a newer moment of the same task replaces it, and a moment that is gone withdraws it. The announced fingerprints (at most 500 per machine) are kept in `notified.json` in the app's private data, so a reconnect or an app restart repeats nothing; a machine's first set only records what is open. Forgetting a machine withdraws its notifications.
- **Android side** (`src-tauri/android/NotifyService.kt`, installed by `scripts/build-android-apk.sh` with the manifest's `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE` and `POST_NOTIFICATIONS` permissions and the `specialUse` service with its `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` reason). The `notify` plugin creates the four channels (the fourth, Connection, holds the minimum-priority ongoing "Connected to your computers" notification of the foreground service), asks for `POST_NOTIFICATIONS` when the owner turns notifications on, raises and withdraws the moment notifications, and opens Android's battery optimisation list on request. The service is started only from the open app and returns `START_NOT_STICKY`.
- **Tap.** The notification's immutable `PendingIntent` opens the app's launcher activity with the machine id, the target and a random key from the app's private preferences. The plugin takes a tap from the activity's start or new intent only with that key, removes the extras and hands it to the next `phone_notification_next` call (the web view waits on it; nothing polls). Rust accepts it only for a paired machine and a closed target; the interface checks it again (`parseTap`, `parseTarget`), switches to that machine if another one is open, closes the phone's own pages and opens the place through the workspace's notification path (`targetPlace`, `openPlace`), as a desktop click does.
- **Setting.** Settings, This phone, **Phone notifications** (`cw.ws.notifications`, on by default) applies once a machine is paired. Its texts and everything Android shows (the ongoing notification, "Connected to your computers" or in Russian "На связи с компьютерами", the channel names and notes, and each moment's title such as "Нужен ваш ответ", "Задача завершена", "Сбой задачи") follow the interface's language (`copy.ts`, English and Russian by the phone's locale). The interface hands them to the native side each time notifications are applied; Rust bounds and checks each one (`moments::words`) and English stays where one is missing, and the plugin keeps the Android texts in its private preferences so the service shows them too. Settings says when Android blocks the app's notifications and, while the app is under battery optimisation, offers **Battery settings**.
- **Limits.** The plugin calls go through the activity's plugin manager, so while Android has destroyed the activity and only the service holds the process, a notification may not be raised until the app is opened again. A phone with battery optimisation or Doze may pause the connection; a moment that came and went meanwhile is not announced. The phone notifies even when it already shows that task. A tap from a notification raised before an app reinstall leads nowhere (the key is new).
- **Verified.** No-paid tests: the moment's shape and fingerprint and the snapshot's changes (`notifier_tests.rs`), the remote allowlist (`remote_policy.rs`), the closed target and that the web view cannot send the subscription (`workspace-client` policy tests), moment validation, priming, deduplication across reconnect and restart, replacement, withdrawal and bounds (`moments.rs`), the subscription through a real loopback tunnel to a real service and tap validation (`tests/phone.rs`), tap parsing and the tap reader (`test/shell.test.ts`), the Settings toggle, tap routing and the battery hint (`packages/workspace-ui/test/phone.test.tsx`). On 2026-11-25 `scripts/build-android-apk.sh --debug` built an arm64 debug APK with the service, permissions and plugin in its merged manifest (a compile check only; the APK was not installed). Not verified: anything on a physical phone or emulator (the foreground service, the permission prompt, notifications appearing, background and Doze behaviour, a tap opening the task, battery settings), and a real machine with projects sending moments to a phone.

## Android build prerequisites

`scripts/build-android-apk.sh` builds the app into one APK under `.workspace-build/android/` (the APK and its `.sha256` file). `scripts/build-local.sh [desktop|apk|all] [--release] [--debug-apk]` runs it, and the desktop package build, on this machine. Nothing here is built in the desktop's Docker container; the script runs on the host and exits 2 for a missing prerequisite.

- Needs: `cargo` with the pinned toolchain and its Android target (`aarch64-linux-android`; `--all-abis` also needs the armv7, i686 and x86_64 targets), `npm`, a JDK 17 (`keytool`, `java`), the Android SDK (`ANDROID_HOME`, default `~/Android/Sdk`) with an NDK (`NDK_HOME`, default the newest under the SDK) and build-tools with `apksigner` and `zipalign`.
- Options: no option builds the dev channel signed with the release key; `--release` builds the release channel (its own application id, installs beside dev); `--debug` builds a debug APK signed with Android's debug key and needs no keystore; `--all-abis` builds arm64, armv7, x86 and x86_64 instead of arm64 only; `--init-signing` creates the signing keystore once, prints the CI secret names and stops. An existing keystore is never overwritten.
- Signing: an update installs over an existing app only when both builds carry the same key, so local and CI builds must use the same keystore. It is read from `CORTEX_ANDROID_KEYSTORE` (default `~/.config/cortex-workspace/android/release.jks`), `CORTEX_ANDROID_KEYSTORE_PASSWORD` (default: the file `<keystore>.password`, mode 0600) and `CORTEX_ANDROID_KEY_ALIAS` (default `cortex-workspace`). The keystore and its password never belong in the repository.
- The build switches Android app backup off in the generated manifest so the pairing key never leaves the phone in a backup.
- Observed: `workspace-remote` and `workspace-client` cross-compile for `aarch64-linux-android`; `scripts/build-android-apk.sh` built a signed dev-channel release APK for arm64 on the development machine. On 2026-11-18 that APK was installed over USB on a Pixel 9 Pro XL (Android 17): it opened on the connect screen, paired through the pasted-link route with a throwaway machine service on the same network (`cargo run -p cortex-workspace-android --example pairing_host`), loaded that machine's empty Home, showed the connection as direct, and kept the Continue button above the on-screen keyboard. Not verified: the QR scan, the fingerprint wait screen with a manual Allow, work on a machine with projects, Back, rotation, large text, reconnect after a network change, a connection from another network, and the GitHub workflow's Android job ([packaging](../project/packaging.md#manual-workspace-releases)).
