# Migration and rollback

**Status: the Workspace keeps its product records in the project's own Cortex store, so there is no separate Workspace import. The automatic format-11 to format-12 store migration with a private backup is implemented ([format migration](../project/format-migration.md)); legacy stores written by the former runtime are not adopted automatically ([local task execution](local-task-execution.md#legacy-task-adoption)). No Workspace-specific migration or rollback rehearsal is recorded (CW-Q05), and no rollback command ships.**

The new client is not a replacement of the existing runtime store. Map stable product task IDs to existing execution identities with an idempotent import and explicit ownership; do not assume isolation or import by parsing prose. Before any migration specify source and destination versions, backups, validation, reversible changes and rollback point. Preserve existing project data and avoid modifying production Paseo. On failed import, retain originals, report partial progress and allow safe retry. Never claim rollback succeeded without rehearsal. Runtime storage format migration remains governed by existing project documentation.

**Sprint run modes.** A sprint saved with the former `automatic` value is read as `hybrid` on its first product read, with unchanged behavior. The next product write persists that translation with `sprintRunModeVersion: 1`, and a sprint created or patched to `automatic` records the same marker. Builds that predate Hybrid do not understand the marker. Mixed-version or rollback use of the service and the interface is not qualified, so keep them at one version. See [sprint run modes](local-task-execution.md#sprint-run-modes).
