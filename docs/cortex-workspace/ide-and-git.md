# IDE and Git

**Status: wider design, partly implemented.** Local desktop Code uses pinned CodeMirror 6 and supports leased edits, revision-checked saves and read-only language tools. CodeMirror-based diff views and the wider GPU-terminal design remain planned. Local project terminals use pinned xterm.js 6.0.0 (DOM renderer), fit addon 0.11.0 and portable-pty 0.9.0; Ctrl+J opens the owner shell at the registered project folder. See [terminal security and limits](security.md#owner-terminal-built-local-linux).

## Code file actions

Above an open file, the **File actions** menu contains **Go to file** (also Ctrl+P), **Open in VS Code** (or **Open in default app**), and **Show in file manager**. Show in file manager asks the Linux desktop to select the current checkout file. If selection is unavailable, it opens the containing folder without selecting a file. Unavailable openers stay in the menu with their reason; Save and the view controls are unchanged.

## Code editing and write leases

Files open read-only. Select **Edit** to acquire a lease for the file in the current checkout. The editor renews it about every 20 seconds; it expires 60 seconds after the last grant or renewal. **Stop editing**, switching files, leaving Code or closing the editor releases it; if a release does not reach the service, expiry is the fallback. A machine reboot invalidates earlier leases.

- **Task … is editing this file.** (`task_file_lease_held`) Edit access is blocked by a runtime-managed writer. Try **Edit** again when it is no longer working on that file.
- **Edit lease lost. Your draft is kept. Select Edit to try again.** (`edit_lease_lost`) The file returns to read-only. The draft remains in the open app, not on disk.
- **The file changed on disk. Your draft is kept.** (`conflict`) Review the new disk version before choosing how to resolve the conflict. Every save, including autosave and an explicit **Keep mine**, needs a valid lease and a matching base revision.

The lease coordinates local Code saves with the same logical project's structured worker file tools in the same Workspace channel. It is not an OS lock: host commands, outside writes from other projects, native engine writes, Git, external editors and terminals are outside the guarantee. Saves still check the disk revision; these checks do not eliminate races with uncooperative writers. See [editing files](local-task-execution.md#editing-files) for buffer and conflict handling.

## Language tools

Local desktop Code shows inline and gutter diagnostics and a **Diagnostics** list for Rust and TypeScript/JavaScript (including TSX and JSX). Use **F12** or **Ctrl/Cmd+click** to go to a definition in the current checkout. These language tools work in read-only Code buffers and do not apply workspace edits, provide completion or format files. **Language services unavailable** (`lsp_unavailable`) means analysis is unavailable, not that the file has no issues; editing and saving still work when a lease is held. While you edit unsaved text, diagnostics follow the current buffer: results computed for an older version of the text are never shown as current, so the list can briefly be empty until the language server answers for the latest edit.

The desktop packages bundle rust-analyzer **2026-11-16**, typescript-language-server **4.4.0** and TypeScript **5.9.3**. In Workspace Dev only, local machine settings accept the optional absolute executable paths `rustAnalyzerPath` and `typescriptLanguageServerPath`; release uses its bundle. See [packaging](../project/packaging.md#bundled-code-language-servers). Remote and Android Code remain read-only and do not offer language tools.

## Git and checkouts

At task creation, choose the current checkout and its currently open branch or a dedicated worktree. Every task reaches Ready to merge: the repository Git default branch is the default target, changeable per task or sprint. Separate branches offer owner-confirmed local merge (squash by default) or PR creation. A task already working in its target branch instead offers confirmed closure for recorded content already committed, a task-scoped local commit for known pending files, or explicit closure when attribution is unknown; automatic sprint mode does not bypass confirmation. No merge is implicit in result acceptance. A local-only repository needs no remote for review, commits, squash merging or closure; network/PR controls and push-status wording appear only with a configured remote. Commit and squash drafts use the configured model to write an English subject and a detailed body from the actual changes. On the Git page, **Generate** reads staged changes when there are any, otherwise pending changes. Only bounded excerpts and a file list are sent to the provider. Drafts are editable; when generation fails, the dialog says why and you can write your own text. Owner-entered text is not translated. See [short model texts](local-task-execution.md#short-model-texts).

For a result you accepted in the project folder on a branch other than the target, ordinary **Git → Commit…** keeps that result current when the app can confirm the commit contains exactly the accepted files and bytes on the same branch. You can stage those files first. Push the branch to `origin` in Git, then choose **Finish → Create a pull request**. Finish does not push. The **Push** and **Pull and push** confirmations use the configured model to draft a **Summary of commits being pushed** from outgoing commit subjects, bodies and aggregate change counts. Git uses local tracking information and does not contact the remote to prepare the draft. You can edit it, type it yourself, or leave it blank and confirm without waiting for the draft. When Push succeeds, Workspace saves the confirmed summary (or clears it if left blank). Create PR / Finish prefills the editable PR **Description** with that summary when it matches the checkout's current head and `origin` destination, without adding a checks paragraph; otherwise Workspace prefills the PR fields from local Git metadata. The owner-confirmed Push records a witness (repository, full commit and remote ref), and Create PR requires that witness plus a read-only lookup of the remote ref that returns exactly the witnessed commit (see Create PR repository binding below). If files were added, removed or changed outside the accepted result, the app blocks Finish and Create PR and asks for a new result. A partial commit, an amend, a branch switch, or an unconfirmable checkout does not get this exception. **View PR** opens an already recorded address; it does not create or update a PR.

The Git tab immediately displays the last confirmed checkout and requests a fresh snapshot on open, including returning to a parked tab. Window focus also requests fresh facts; visible-window polling catches external changes at 30 seconds, backing off to 120 seconds when unchanged. Reads share an in-flight snapshot and publish its completion without requiring a manual refresh or rereading task history. Failed reads retain confirmed facts and retry on the next open, focus or poll. Untracked files in nested dependency/cache directories are enumerated individually unless Git ignores them; reserved private helper state remains hidden. Above 2,000 untracked files in one checkout, each directory Git reports as wholly untracked becomes one Untracked entry without a preview, smallest directories expanded first while the limit allows (files beside tracked files stay individual), and Code lists such a folder closed and reads its contents when it is opened. Staging or committing a collapsed entry includes its whole directory. This does not change `.gitignore`, stage files, commit, or fetch remotes. An already installed desktop needs a rebuilt package and a later app/service relaunch to use changed bundled UI/helper code.

## Title band actions

On the desktop, the title band of a task and of a project page holds two split buttons at its right, side by side; the phone shell has neither. They act on the task's own checkout (its worktree, or the project folder it shares), or on the project folder when no task is open. Every action is an existing service operation behind its existing confirmation: nothing here forces a push, resets, stashes or discards.

**Open.** The main half opens the checkout where the owner last chose; the first time it is the external editor when the machine has one (VS Code, or the default application when only that is found), otherwise the Code tab. The chevron lists only what is available here: the external editor through the same validated opener as Code's Open in VS Code (fixed program names and arguments, the folder resolved by the service), Open in Code tab, and Open terminal here, which opens the app's own terminal panel at the project folder; a task's worktree has no terminal of its own, so that entry is left out for it. File-manager selection is offered for an open file in Code, not for a checkout from the title band.

**Git.** The main half is the one next action for the state, chosen in this order:

| State | Main action | What it does |
| --- | --- | --- |
| A pull stopped at a conflict in the checkout, or a merge or rebase stopped there from a terminal. A stopped target-to-source update is not this state: use the [saved merge’s conflict view](local-task-execution.md#integration-and-conflicts), not the pull controls | Resolve conflicts while files remain in conflict, then Continue merge or Continue rebase | Resolve conflicts opens the Git page, which lists the conflicted files. Continue finishes the pull once they are marked resolved; a rebase can stop again at a later conflict, and the pull then stays stopped with that conflict listed. Abort merge… or Abort rebase… (Git menu and Git page) returns the checkout to where it was before the merge or rebase began, and Cortex checks the result afterwards. Exact restoration is established for the clean case: a pull Cortex started on a checkout with no uncommitted tracked changes, which Cortex requires before it starts. A merge or rebase started in the terminal was not checked by Cortex before it began. If the checkout after the abort does not match its earlier state (HEAD, branch or tracked files), or Git no longer records where a rebase started (then nothing is aborted), Cortex reports that the restoration is not confirmed and asks the owner to inspect the checkout in the terminal (Ctrl+J); nothing else is changed or retried. A rebase that stops without a conflict, for example on an emptied commit, is likewise left for the owner to inspect in the terminal or abort. While the pull is stopped, Commit…, Pull, Push and Pull and push are off with "A pull is stopped in this checkout. Continue or abort it first." |
| The task's result is ready to merge and under review, with Git, not already in the target | Review and merge…, Merge…, or Commit to <target>… on a task that works on its target branch | Opens the Finish dialog (squash merge, pull request, or the task-scoped commit). This is the task's primary action, so it is drawn as one. |
| Uncommitted files in the checkout | Commit… | Opens the commit dialog described below. |
| Ahead of and behind its upstream (diverged), when no row above applies | Pull…, which opens the Pull dialog | The histories diverged, so a fast-forward pull cannot bring the remote commits in. Pull… opens the dialog described below, where the owner chooses Merge or Rebase. In the Git menu, Push is off with "The remote has commits you do not have. Pull first. The local and remote histories diverged. Choose Pull… to merge or rebase the remote commits, then push.", and Pull and push is off with "The local and remote histories diverged. Choose Pull… to merge or rebase the remote commits, then push." Cortex never force-pushes. A pull that is refused anyway (the remote moved since the last fetch) pushes nothing and shows the pull's reason. |
| Behind its upstream | Pull | Pulls with fast-forward only. |
| Ahead of its upstream | Push | Opens the push confirmation (remote and branch). |
| Anything else | Up to date | Opens the menu, where every item says why it is on or off: nothing to commit, pull or push in the last fetched state, no upstream to compare with, or a local-only repository with no network action. |

After a successful **Update from target** (including one completed with **Finish merge**), the task’s **Changes** tab compares against the target commit that was merged. Target-only changes are no longer listed; any differences introduced by the task or by conflict resolution still appear. If you commit the stopped merge in Git, use **Finish merge** while that merge commit is still HEAD. Workspace verifies that it joins the saved task and target commits before changing the comparison base. **Abort merge** leaves the previous comparison base unchanged. After conflict resolution, **Request fresh checks** requests independent review and runtime verification for the resolved revision; the earlier checks do not apply.

Ahead and behind count only against an upstream; without one the service's counts are against the target branch and never suggest a pull or a push. Beside the button, ↑ and ↓ give the commits ahead of and behind the upstream, and a dot with a number the uncommitted files; the counts are left out when they are zero, and on a narrow band.

In an Automatic sprint the queue makes the same-branch commit itself after automatic acceptance, so the owner does not press Commit for those tasks. A task whose target differs from the current branch waits for owner confirmation instead ([sprint run modes](local-task-execution.md#sprint-run-modes)).

The Git menu and the Git page apply the same rules but disable different things. The menu disables each item before it opens anything, and says why. On the Git page, the Pull button opens the Pull dialog on diverged histories even when tracked changes or a live task are present; the dialog then gives the reason the menu gives ("Commit your uncommitted changes first. A merge or rebase over them could not be aborted exactly, and nothing is stashed." or "A task is working in this checkout. Stop it first.") and does not pull. The Push button is not disabled by divergence: it opens the push confirmation, and a push the remote does not accept as a fast-forward is refused as `push_not_fast_forward`. While a pull is stopped, the Git page's Pull button is off with the stopped-pull reason.

The chevron lists every action in one fixed order, each on, or off with its reason as the menu row's second line: Commit… · Fetch · Pull (Pull… on diverged histories) · Push · Pull and push · Resolve conflicts, Continue merge or Continue rebase, and Abort merge… or Abort rebase…, while a pull is stopped in the checkout · Update from <target>… · Merge locally… (Commit to <target>… for a task on its target branch) · Create PR… · View PR · Archive task. Fetch, Pull, Push and Pull and push appear only with a configured remote, as everywhere else a local-only repository gets no network control. Update from <target>… appears only for a task with a worktree of its own on a branch other than its target, and only where the machine offers `update_from_target`. Two other places carry the same action under the same condition, with different gates. The worktree menu of the Worktrees page lists it for such a task and shows it off with its reason when the machine does not offer the update, or when the task is not finished. The Finish task dialog shows its Update from <target> button only when such a task is behind its target and the machine offers the update; otherwise it shows no such button. For a Cortex-owned worktree, update the source explicitly before squashing if the target has moved. Update requires fresh review and verification; confirmed squash uses committed source and changes only the selected safe target. Finish offers **Delete worktree folder**, checked when eligible and disabled with a reason otherwise. See [separate worktrees](local-task-execution.md#separate-worktrees) for the checkout and cleanup lifecycle. Merge locally…, Create PR…, View PR
and Archive task need a task on view and are left out on a project page; Create PR… also needs a remote. The reasons an item is off include "Nothing to commit", "No upstream branch", "Nothing to push", "Result not accepted yet", "A pull request is already open for this version", "GitHub CLI not available" and "A merge of this task is in progress. Resolve or abort it first." **Archive task** does not change Git, so it is available even during a conflict. It asks for confirmation on unfinished tasks; see [Archive](local-task-execution.md#archive-and-service-owned-work). When browser opening is supported, **View PR** opens the recorded pull request address from either the Git menu or the merge card. If GitHub CLI did not report an address, the menu explains why **View PR** is unavailable and the card shows the same explanation instead of a button.

A main action that cannot run here (the machine does not offer it, or it is offline) also opens the menu instead of sitting dead; only Merge… is ever off in the band, and then the task page says why. While an action runs, its main half shows its progress (Pulling…, then Pushing… for Pull and push) and every menu item except View PR and Archive task is off with "Another Git action from this button is still running." View PR stays on while another action runs, when its recorded address and opener checks pass, because it only opens that address in the browser and does not change the checkout. A refusal or failure, including the service's immediate refusal while another fetch, pull, push, commit or merge of the project runs, opens beside the button in the service's own words, with Retry for each action that can be repeated from it (Fetch, Pull, Pull and push, Continue, Abort and View PR). A merge or rebase pull and Update from target show their refusal inside their own dialog instead, with a link to the conflict where one was left. The service classifies the refusals of push, pull and fetch from Git's own output without showing it (every other Git command keeps `git_failed`): a push that is not a fast-forward (`push_not_fast_forward`), a pull that cannot fast-forward (`pull_not_fast_forward`), no upstream (`upstream_required`), rejected credentials (`git_auth_failed`), an unreachable or missing remote (`remote_unreachable`), a hook's rejection (`git_hook_rejected`) and a protected branch (`push_protected_branch`), each saying what was not done and what to do next; anything else stays `git_failed`.

**Pull dialog.** On diverged histories, the band's main action, the Git menu's Pull… item and the Git page's pull button open a dialog titled "Pull into <branch>" instead of pulling. It states, as counted at the last fetch, how many commits this branch has that its upstream does not and how many the upstream has that this branch does not. Under "How to bring in the remote commits" it offers **Merge** (one merge commit joins both sides; nothing is rewritten) and **Rebase** (this branch's commits are replayed on top of the upstream for a straight history and get new identities). Merge is selected first. The one button reads "Pull with merge" or "Pull with rebase", and "Nothing is pulled until you confirm." is its hint. The dialog says that pulling fetches the upstream again first, so it can bring in newer commits than the counts show. Nothing is pushed, stashed, reset or forced. If both sides changed the same lines, the pull stops at the conflict and stays stopped in the checkout until the owner resolves it in Git and continues, or aborts, which returns the checkout exactly to where it was. The button is off with its reason on a detached HEAD ("This checkout is not on a branch (detached HEAD)"), while a pull is already stopped there ("A pull is already stopped in this checkout. Continue or abort it first."), and while a task works in the checkout ("A task is working in this checkout. Stop it first."). Uncommitted tracked changes are refused with "Commit your uncommitted changes
first. A merge or rebase over them could not be aborted exactly, and nothing is stashed.", beside a Commit… button; untracked files do not count. A refusal from the service stays in the dialog, with a Resolve conflicts link when a pull was left stopped, and the dialog closes on success. The service runs `git pull --no-rebase --ff --no-edit --no-autostash` for Merge and `git pull --rebase --no-autostash` for Rebase. An ordinary Pull, when the checkout is behind and not diverged, runs `git pull --ff-only`.

**Update from target.** The Git menu's Update from <target>… item, the worktree menu on the Worktrees page and, when a worktree task is behind its target, the Update from <target>… button of the Finish task dialog open a dialog titled "Update <branch> from <target>?", whose one button reads "Update from <target>". It says that the new commits of the target are merged into the task's branch in its worktree, that the target is not changed and no commit is rewritten; that the result reviewed before becomes no longer current and any acceptance of it is withdrawn, so fresh review and verification are required before it can be merged; and that a conflict stops the update in the source checkout. Uncommitted changes in the worktree are refused with "The task's worktree has uncommitted changes. Commit them first; a merge over them could not be aborted exactly, and nothing is stashed." and a Commit… button. The item is off with one of "Available for a finished task", "Available once this task has a result", "Up to date with <target>", "The task's worktree has uncommitted changes. Commit them first; nothing is stashed.", "A merge of this task is in progress. Resolve or abort it first.", "A pull is stopped in this checkout. Continue or abort it first." or the live-task reason. The service runs `git merge --no-autostash --no-edit` into the task's branch and refuses with "The task's branch already contains every commit of
<target>. Nothing was changed." when there is nothing new. On success the dialog closes and the task opens on its Changes tab. If the update stops at a conflict, **Open the conflict** leads to [the saved merge controls](local-task-execution.md#integration-and-conflicts): finish manually or explicitly hand it to Cortex. Use **Inspect merge state** if the outcome cannot be confirmed. **Abort merge** is available only for a confirmed stopped merge under owner control. None of these controls changes the target. For a [saved merge from an earlier version](local-task-execution.md#saved-merges-from-an-earlier-version), finish or abort in the original checkout using Git first, then confirm **Clear saved merge…** in Workspace. Clearing does not change Git or restore previous checks.

**Create PR repository binding.** Create PR runs `gh pr create --repo HOST/OWNER/REPO` with the repository parsed from the single effective `origin` URL (fetch and push must agree; HTTPS, SSH and SCP-like forms are accepted), together with the exact head, base, title and body. The child process drops `GH_REPO` and any conflicting `GH_HOST`, so ambient GitHub CLI overrides cannot redirect the pull request. Create PR also requires a push witness: when the owner-confirmed Push to the single eligible `origin` completes, Workspace pins the full commit and exact `refs/heads/<branch>` in the push and records, privately and keyed by remote ref, only the canonical host/owner/repository the push reached, the full commit SHA and the remote ref. A later successful push without usable evidence clears the previous witness. Before `gh pr create`, Finish refuses (nothing is dispatched to `gh`) when the witness is missing, when today's fetch and push destinations no longer identify the witnessed repository (for example `origin` was retargeted after the push), or when a read-only, repository-scoped `gh api` lookup of the branch does not return exactly the witnessed commit (the remote branch moved). This ties the pull request to the commit that was pushed, not merely to the local `origin` tracking ref; it narrows but cannot eliminate a provider-side race between the lookup and the creation. After creation the printed address is checked and a separate repository-scoped read must match repository, source ref, full head SHA, base branch, open state and exact address before it is saved; missing, mismatched or ambiguous evidence saves nothing and the creation is never replayed. The reported address must be an https pull request address on the same host, owner and repository; any other result, including another repository on the same host, is refused (`pull_request_unsafe`) and nothing is saved or opened.

**View PR.** When a task's pull request was created from Cortex, the address GitHub CLI reported is recorded only if it is an https address of the repository behind the origin remote (same host, owner and repository). View PR checks the saved address against the current `origin` again and refuses it if the repository changed. The merge card of an accepted task then shows a row "Pull request created into <target>" with that address and a **View PR** button, and the Git menu has the same item after Create PR… and before Archive task. Pressing it asks the desktop to open the recorded address in the system browser. The request names only the project and the task; the service looks the address up, and the desktop accepts only a plain https address before starting the browser opener. The item is not offered, and the card shows the address as text without a button, where the desktop finds neither `/usr/bin/xdg-open` nor `/usr/bin/gio`. When GitHub CLI reported no address, the item is off and the card reads "GitHub CLI did not report this pull request's address, so it was not recorded. Find it on GitHub." with no button. A refusal carries its own message: the service's words for a refused lookup, otherwise the desktop's, such as "No browser opener is installed on this machine." The press can be repeated. In [extracted Dev qualification](testing-and-acceptance.md#extracted-dev-readiness-gates), both entries record the address digest through the native recorder instead of opening a browser. Extracted Dev without a recorder does not offer View PR.

**Commit dialog.** It shows how many files are staged, unstaged and untracked, the files themselves (the first eight), and that Commit includes every change when nothing is staged, as the Git page's commit box does. A saved draft message is kept; otherwise, for a task's checkout, the machine writes a message from those files and the task text, said as "Writing from the changes…" and then "Written from the changes" or "Listed from the changed files"; text the owner types is never replaced. Nothing is committed or pushed until Commit is pressed. When a task is working in the checkout, the dialog says so and Commit stays off until the owner chooses Stop the task first or Commit anyway, the same choice the Code screen offers before saving. Stage files in Git opens the Git page for finer staging.

The Git button is a status line, not a Git screen: its project's Git facts are read when the page opens, with the facts its task's own state changes and file writes already bring, after any Git action of the owner (from the button or anywhere else), on return to the window when older than ten seconds, and when its menu opens (the last state stays on view and is updated in place). It never adds a timed read: the 30-second visible refresh stays with the Git page, Worktrees, Code, the Changes tab and the Finish dialog. Fetch, at the top of the menu's network group, reads the upstream on request.

Current CLI status, diff and log inspection disables configured clean/smudge/process filters through per-command options, so missing required filter programs do not break reads. No Git configuration is rewritten. Filtered content remains labelled; writes keep normal hooks and filters.

Code opens Markdown, CSV, TSV and SVG formatted with a one-click switch to source, shows HTML and JSON as source with a sanitized preview, shows pictures and plays video and sound inline, and gives PDF and other binary files a placeholder; see [viewing files](local-task-execution.md#viewing-files). Code's tree shows every file and folder in the project folder, dot-files and files Git ignores (such as `.env` and build output) included and dimmed; folders outside what Git reports are read one level at a time when opened, never walked eagerly; see [the file tree](local-task-execution.md#the-file-tree).

The native Rust machine path uses installed Git argv for status/diff/log/index operations as well as commit, branch, fetch, pull and push, preserving installed Git semantics without a Python machine helper. Core-owned integration and runtime-writer checks still use the migration provider; see the [native machine boundary](local-task-execution.md#native-machine-boundary). Validate behavior rather than promising perfect equivalence. Show exact worktree identity and changes before mutation. Dirty branch changes and merge conflicts remain visible; never auto-stash/reset. Confirm remote and branch before push; never force push or auto-retry an ambiguous push. Accepting a result does not commit or push. VS Code is not the base; optional Open in VS Code is a separate action that opens the task’s resolved checkout folder, with a visible unavailable reason. Discovery also checks per-user launcher folders; it does not start an editor to test availability.
