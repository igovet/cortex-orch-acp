# Public contract and events

**Status: planned product contract. The local desktop slice in the last section is built; each operation is advertised only when its implementation is wired, and the no-paid checks are listed in [verification](../project/verification.md).**

Planned adapter: negotiate protocol version and capability set; return typed project/task/execution/decision/result summaries and explicit unknowns. Commands identify project, actor/device, operation, request ID, expected entity version and owner epoch where relevant. The server checks authorization, version and state before changing anything. A matching request ID and payload returns the original receipt; reuse with different payload is rejected. Concurrent distinct decisions permit one winner; stale, expired or revoked operations fail explicitly.

A snapshot and cursor must share an atomic consistency boundary. A public project outbox emits monotonically ordered events; replay from a retained cursor, deduplicate, detect gaps and resnapshot if retention expires. Bounded history and fan-out must not silently drop state. Unsupported generic ACP features remain unavailable; never infer verification from conversation text. External side effects such as Git push require an explicit unknown-outcome state and reconciliation, not automatic replay.

## Local desktop slice (built)

The first implementation covers only the subset below. It is the contract of [CW-S02](backlog/CW-S02.md) to [CW-S12](backlog/CW-S12.md) and is described in [ADR 0014](adr/0014-local-service-transport.md). The wire version is 1.8 and the mapping version is 1.

**Transport.** The desktop shell reaches the service through a native bridge. The service listens on a Unix domain socket in a private runtime directory. Frames are length-prefixed UTF-8 JSON with a 4-byte big-endian length and an 8 MiB maximum, carrying JSON-RPC 2.0 requests and bounded subscription notifications. ACP keeps its own newline-delimited framing. No TCP, loopback HTTP or WebSocket listener is used.

**Operation layers.** The service handles these local operations itself: `service.status`, `service.capabilities`, `service.subscribe`, `service.stop`, `projects.register`, `projects.rename`, `projects.list`, `projects.status`, `projects.activate`, `projects.resynchronize`, `executions.cancel`, `executions.prompt`, `executions.control`, `directories.search`, `directories.cancel` and `machine.call`. `executions.cancel` resolves the public execution through the adapter and requests cancellation only of its bound ACP session; the response says that cancellation was requested, not that the run has stopped. `executions.prompt` durably captures an identified owner message through the existing steering path, including during a running turn; `recorded` means capture, not execution. Continuation consumes it at the turn boundary. `executions.control` resolves the same execution before forwarding the closed worker-message, worker-stop and command-stop controls to `_cortex/workspace_control`. These controls require a live owning session, not just a retained execution row. The built service advertises no session-option or permission operation. The schema reserves `sessions.options.*` and `permissions.*` as service operations, but they are not advertised. Adapter operations are sent to Cortex as `_cortex/workspace`: `capabilities.get`, `project.snapshot`, `tasks.list`, `tasks.get`, `tasks.create`, `executions.get`, `events.page`, `requests.get`, `results.get`, `decisions.list` and `decisions.get`. `tasks.start` and `decisions.answer` are advertised only when activation has bound their handlers. `history.page` is advertised and served from the durable display transcript/update sequence. Pages retain source order with a project/task/session/page-size-bound cursor and a frozen high-water mark; invalidations trigger a fresh read. User and coordinator text, plans and tool titles/status survive reopening; raw tool arguments, results, thoughts and private reports are excluded. Unknown or oversized display content is explicit, not silently clipped. The shell exposes a closed allowlist; it cannot forward arbitrary methods or paths.

**Saved task editor and sprint archive.** These extend the existing local `machine.call` helper, not the public adapter wire operation list: `product.task` action `edit` delegates to the adapter's host-only, version-checked draft write; `product.sprint` action `close` records a confirmed archived timestamp. The generated wire schema remains 1.8. Title, description, attachment bytes and options commit in the draft's SQLite transaction; the helper projects the saved title over auxiliary naming. A stale version or any execution identity refuses editing. Sprint closure is idempotent, keeps member state and files, and disables further sprint mutations. Closing and scheduler starts serialize through the existing owner-record lock; the scheduler rereads the current task version before claiming a start. See [editing and closure](local-task-execution.md#editing-saved-tasks-and-closing-sprints).

**Action acknowledgement and refresh.** The window settles receipts before projection synchronization. Task/sprint actions reread only their project and show Updating confirmed state separately; registry changes still refresh capabilities and project membership. A read begun before a newer command reply cannot overwrite that reply’s confirmed rename/queue fields. Refusals and unknown outcomes remain failures and are never replayed. The fixed machine-helper operation `product.facts {taskIds}` returns `{product, workers}`, composing the existing readers under one helper startup; Git inspection runs separately and overlaps. It is not a single SQLite snapshot across the product file and worker database, and does not change the generated wire version or mutation checks.

**Permanent sprint deletion.** The owner command `delete_sprint {projectId, sprintId, confirmed}` maps to `machine.call` operation `product.sprint` action `delete`. The service owns preparation, task-wide cancellation and bounded completion; internal `delete_prepare`/`delete_finish` helper phases persist a start fence and retry state. The response is `{done, taskIds?, keptPaths?, reason?}`: `done: false` is explicitly incomplete, not successful deletion. Completed results replay idempotently by sprint identity. This extends the machine-helper contract, not the generated ACP adapter operation list; the wire schema stays 1.8. See [deletion and file preservation](local-task-execution.md#editing-saved-tasks-and-closing-sprints).

**Coordinator activity and observed routes.** `history.page` rows optionally include
typed worker-shaped `activity`; bookkeeping is hidden while continuation still
consumes its sequence. The machine `workers` helper exposes that same retained
feed through `workerId: "coordinator:<taskId>"`, with the task in `taskIds`, without
adding a coordinator to ordinary worker lists. Task list/detail adds nullable
`coordinatorRoute`. Worker list/detail uses each provisioned engine attempt's native
configuration confirmation for `route`, not dispatch intent or machine defaults;
`routeAttempts` retains the audited fallback chain. Both route objects contain
readable `model` and `effort` strings only. An unconfirmed route is null; an
unreported effort is empty. See [recorded data](local-task-execution.md#recorded-data-and-pending-questions).

**Machine versus project state.** `service.status` alone decides whether the machine is connected. A refused, slow or failed request is that action's answer and never changes the connection. `projects.register` takes `{root, displayName, create?, newFolder?}`: `root` is any folder the owner can write to, `~/` is the owner's home, links are resolved once, and `project_folder_missing` is returned until the caller sends `create: true`. `newFolder: true` creates exactly that one folder inside an existing parent, returns `project_folder_exists` when the name is taken, and removes the folder again if registration is refused. `projects.rename {projectId, displayName}` changes only the name shown. `projects.status` reports `state` (`ready`, `starting`, `recovering`, `failed` or `inactive`) with a stable `reason` code. An activated project with no working child stays registered and the service restarts its controller with backoff (never a task); `service.subscribe` announces `project_state` when a child starts or stops, and the desktop rereads capabilities. `native.pick_folder` is the desktop's own folder chooser. It is answered by the shell, not the service. The bridge marks a refusal `refused:<text>` so a client can tell it from a reply that never came, which stays an unknown outcome.

**Folder search.** `directories.search {session, query, limit?}` finds folders on the machine for the Add project flow, and `directories.cancel {session}` stops one. Shared closed Rust types live in `crates/workspace-protocol/src/directories.rs`: a client sends only the text the owner typed, and `limit` is 1 to 100, 30 by default. The reply is `{query, home, entries:[{path, git}], complete, stopped?, scanned?, cancelled?}`. `query` echoes the request, `home` is that machine's home, `git` says a `.git` exists there, and `complete` is false when a limit ended the walk. A blank query answers at once with the home and starts nothing. A newer search in the same `session` replaces the one before it, which answers `cancelled: true`.

The service runs `crates/workspace-service/directory_search.py`, one process per search and at most two at a time, and chooses every root and limit itself. A typed path anchors the walk under its parent; a fragment walks the home, `/mnt`, `/media`, `/srv` and the parents of registered projects, all inside the allowed root. The walk is breadth first, reaches 12 levels, 20,000 folders, 200,000 directory entries and 50,000 entries per folder, and stops after two seconds. After 5,000 folders it stops as soon as it holds a confident match. A helper stuck in a read answers with what it has shortly after the deadline, and the service kills it at four seconds with `directory_search_timeout`. It skips unreadable folders without an error, hidden folders unless the typed name starts with a dot, build output such as `node_modules` and `target`, every `.cortex`, and the service's private state and runtime directories. Links are offered, walked only while they stay in the tree, and each real folder is walked once, so a link loop ends. It reads directory entries and asks whether `.git` exists; it never opens a file. Like every other request it never changes the machine's connection.

**Owner terminal.** The local service separately advertises `terminal.open/read/write/resize/close`; these are not Python adapter or model MCP operations and do not use the durable mutation ledger. Shared closed Rust DTOs live in `crates/workspace-protocol/src/terminal.rs`. Open carries `{projectId,cols,rows}`, read carries `{projectId,sessionId,after}`, write carries `{projectId,sessionId,data}`, resize carries `{projectId,sessionId,cols,rows}`, and close carries `{projectId,sessionId}`. Open/read return `{sessionId,data,next,truncated,exited}`, with byte-array output and a safe-integer byte cursor; a gap is explicit. Write returns the accepted UTF-8 byte count, including a possible short write, never a command-completion receipt. Resize/close acknowledge `resized/closed`. Open reattaches the project's existing session and returns its retained tail. A lost response never replays input; explicit reconnect reattaches output only. The service, not the client, resolves the initial project cwd and user's shell. See [authority, bounds and cleanup](security.md#owner-terminal-built-local-linux).

**Machine helper.** `machine.call {op, projectId?, params?}` runs `crates/workspace-service/machine_tools.py`, one bounded process per call, for what is not a runtime fact: Git status, history and actions; file reads and owner saves; worker activity read-only from the project store; Cortex settings through the configuration management API with its revision checks; machine settings, storage, diagnostics and cleanup; and the owner's own records. `op` is a closed set checked by both the bridge and the service. `repo.file` returns a file's text with its `revision` (the SHA-256 of its bytes), `readOnly` and `writer`. `repo.file.save {checkoutId, file, text, revision}` answers `saved` with the new revision, `conflict` with the current one (null when the file is gone) or `writer_active` with the task holding the checkout; `revision: null` means the file must not exist. `repo.locate` is the service's alone: the bridge asks it where to open a file, and a page cannot call it. The service supplies the project root and state directory itself, so a client names only a registered project and a path inside its checkout. These facts move without the runtime's project version moving, so they are not projections: each read replaces the last one for that project, and the app rereads them on a short poll. Owner records (titles, acceptance, Ready to merge, closing, archive, sprints, unsent queue and review comments) live in the service's private state as `product/<project>.json`, never in a project's `.cortex`. Archive purge now removes the bound runtime and adapter rows through journaled cleanup and attempts SQLite space reclamation. Active or unknown executions are protected; unmerged work requires the owner decision. See [task execution](local-task-execution.md).

**Local Git and review facts.** `repo.snapshot` and `product.read` expose `hasGit`. A non-Git snapshot still contains the project file tree and its main-folder checkout; Git-only controls must not be inferred from a non-null snapshot. Initialize explicitly through `machine.call {op:"git", projectId, params:{action:"git_init"}}`; the service also accepts the project-scoped `op:"git_init"` alias. This only runs `git init`, refuses an existing repository and returns `{done:true, hasGit:true}`. A native bridge with a closed operation list must allow the alias before using it; the existing `git` route avoids needing that extra bridge operation. No commit, remote, account configuration or task start is implied. `product.read.tasks[taskId].reviewActions` exposes the owner review gate; see [review behavior](local-task-execution.md#integration-and-conflicts). These helper facts are reread independently of runtime projection versions.

**Mutation envelope.** `{protocol:{major,minor}, requestId, projectId, actorId, operation, target, expectedVersion, ownerEpoch, payload}`. `expectedVersion` is 0 for creation and a positive per-entity version afterwards. `ownerEpoch` is required for execution and decision authority and is null before ownership exists. The service derives the actor from the authenticated local peer, so client JSON cannot choose another actor. Public sequence numbers, versions and epochs are decimal strings. Result Accept sends `results.get.version` (the UI's `sourceVersion`) with the reviewed digest to `product.task`; the displayed result sequence is not that source version. The persisted acceptance retains the source version, and the UI labels it with the matching result sequence. A rerun that records a technical blocker still changes evidence: refresh the source version before accepting. Control replies with a refusal outcome and message are not successful no-ops.

**Receipt.** `{requestId, outcome, target, entityVersion, executionId?, ownerEpoch?, reason?, recordedAt}`. Outcomes are `recorded`, `already_resolved`, `stale_version`, `stale_epoch`, `superseded`, `expired`, `unauthorized`, `unsupported`, `busy`, `invalid_request`, `payload_conflict` and `unknown_outcome`. A recorded request is not displayed as completed work.

**Idempotency.** A key binds actor, project, request identity, operation and a canonical payload digest computed by the server. The original receipt is stored in project storage. The same key with the same input returns that receipt; a changed input conflicts. An ambiguous command is looked up by request identity before any retry. Prompt text is never used as a deduplication key.

**Identity.** Public task identity, public execution identity, runtime task identity and ACP session identity are distinct. A runtime plan revision is not the public entity version. A generic ACP session identifier is never returned as a task identifier.

**Mapping version 1.** Runtime lifecycle maps to public phases as follows: draft without execution is `not_started`; CREATED, PLANNING and PLAN_READY are `planning`; EXECUTING is `execution`; REVIEWING is `review`; VERIFYING is `verification`; RECONCILING and ANSWER_READY are `finalizing`; WAITING_USER is `waiting`, with the wait reason shown separately; RECOVERING is `recovery`; PAUSED is `paused`; BLOCKED is `blocked`; FAILED is `failed`; CANCELLED is `stopped`; COMPLETED is `result`, which is not human acceptance. A missing, unrecognized or contradictory value is `unknown` with a warning. Percentages and time estimates are never produced.

**Local dictation.** The owner-only native/socket surface additionally offers closed voice.start/read/stop/cancel controls, separate from the ACP/project wire schema. Start binds a request identity; further calls bind a random local session identity. Replies contain bounded phase, percentage, seconds, transcript and fixed error code, never audio. One read-refreshed capture lease is allowed; ten seconds without reads or service stop cancels it. Stop finalizes a preview, never a prompt. No path, URL, executable, environment or send parameter is accepted. See [voice input](local-task-execution.md#local-voice-input).

**Task options.** `tasks.create` may carry saved per-task settings and main/worktree checkout kind. Settings apply only to that task; the owning session accepts idle composer changes through `executions.control` with action `task_settings`. Worktree creation uses the configured machine root and the shared logical project store. Automatic queues advance in the activated service child, never from a screen read. `projects.remove` removes the locator and stops its child without deleting the repository/store; native `native.open_editor` resolves a registered project before invoking the installed editor. See [task execution](local-task-execution.md) for unavailable features and safety limits.

**Start.** Saving a draft never starts an execution. An explicit start is idempotent by request identity. `busy` means the target task already has an execution, not that another project task is active. Other Workspace executions, unbound/unknown starts and ordinary ACP tasks never refuse a different task's start. Conversely, pending, unknown or running Workspace starts do not block a new ordinary ACP first prompt; source-event replay still returns its original task. Version, owner-epoch and host readiness checks still apply. A start is recorded and claimed before it is dispatched into a fresh ACP session; a crash leaves that task's execution unknown, and the operation is never replayed automatically. Sprint queue dependency selection and pausing belong to the service scheduler; manual `tasks.start` has no sprint-order check. An `end_turn` stop is not completion.

**Questions and answers.** Durable pending questions are read by question identity, option identity, batch membership, execution and session binding, owner epoch and per-decision version. An identified single or batch answer is all-or-nothing. A winning answer triggers the existing continuation. When the activated adapter advertises `attachments: true`, each answer may carry `attachments: [{name,mimeType,data}]`; multiline text is delivered unchanged. The whole submission is bounded to eight files and 4 MiB decoded bytes. Answer resources and runtime source references commit with the winning answer; stale input captures nothing. `executions.prompt` accepts the same optional attachments and snapshots them through the ordinary prompt-resource path. Queue records retain the bytes privately; Edit restores them. See [attachment behavior and limits](local-task-execution.md#attachments).

**Results.** A result has a result identity and version, an execution binding, text, evidence references and digests, checks with explicit outcomes, and an optional observed workspace digest. A missing check is `not_run` or unknown, never a pass. `sequenceNumber` is the plain result ordinal displayed to the owner (first result is v1); the entity `version` remains separate for reconciliation and digest binding. Acceptance and merge are not part of the result contract.

**Worker activity and delivery.** The machine helper projects real assignment, prose, tool and command-control rows. One attempt-bound continuation pages both task events and command-control/guidance, carrying both namespace positions. A worker DTO is bounded to 64 KiB and 200 combined events; snapshots share a 512-KiB history budget with a 768-KiB envelope ceiling. Deferred rows retain their continuation. Oversized metadata refuses explicitly; text clipping names the retained/original byte counts and leaves stored content unchanged. Older guidance includes delivery status and attachment names. Task-only legacy cursors require reopening history. Direct owner text and optional attachments are recorded for one live worker channel, then resource references are delivered at its next successful Cortex call. Delivery records response construction, not model acknowledgement/action. No immediate-interrupt, withdrawal or fallback-to-next-prompt claim is made. Native engine actions have no Cortex command-stop receipt.

**Task pause.** Owner controls distinguish durable task pause/resume, confirmed terminal close, and engine-turn cancellation. Pause records the previous state and task-level question identities and commits public versions/invalidation in the same transaction. It does not reject merely because background progress advanced the display version; Resume does check that version and owner epoch. A paused task rejects model mutation and cannot answer a question. Explicit Resume after restart restores only the exact recorded session metadata and re-enters the runtime continuation path. Pending worker question/access waits retain their identities too. The runtime fences old worker channels and records a new-attempt continuation with the saved decision, revalidating access rather than transferring the old grant. Unknown outcomes still block replacement. Resume is not a user message or answer. Individual worker cancellation still ends its waits. These controls are not model MCP tools.

**Worker reports.** `reports.read` returns only published reports referenced by retained worker results in the selected project. The shared ReportQuery/ReportPage schemas define its bounds. The reader checks the immutable digest and report-bound cursor and returns at most 4,000 characters, with total character count, partial flag and next cursor. Private runtime state and arbitrary paths are not report targets.

**Review requests.** Review comments are stored as drafts and marked sent only after durable prompt capture. A check rerun is a retained-result-bound runtime control, not a prose request to a model or a client-supplied command launcher. The server resolves the exact retained command and checkout, records the request before execution and uses its verification runner. A recorded request alone is not a pass. Only fresh complete matching evidence closes the check; technical launch/policy blockers remain visible as check metadata. Open worker-check acceptance requires both that recorded technical reason and explicit owner acknowledgement. Steering clears stale acceptance/Ready-to-merge overlays; live runtime work wins over a stale overlay.

**Events and snapshots.** The public project outbox sequence is separate from runtime, task-event and transcript sequences. A snapshot and its high-water mark come from one read transaction. Clients reconnect with a snapshot followed by events after the cursor, ignore duplicate events, reject backwards entity versions and resynchronize on a gap or an expired floor. Each in-scope writer appends its event in the same transaction as its state change.

Capability replies to a version-1 client at minor 6 or earlier retain its original 1-MiB advertised frame bound; new peers advertise 8 MiB. Limit negotiation intersects only fields both peers supplied. Existing small requests without attachment fields remain valid. Large screenshots require updated transport components; an older peer is never promised the larger budget.

**Sprint checkout.** The owner-only `product.sprint` create command also accepts optional `checkout: {kind: "main" | "worktree"}` and retains it with the sprint. Only those two kinds are accepted; paths and branch overrides are refused there. The port copies that kind into each materialized task’s existing `tasks.create` payload, so `tasks.start` and the automatic scheduler use the same per-task preparation. Planning itself creates no checkout. This is an optional owner-product field, not a change to the generated runtime wire schema (1.8); older sprints without it keep their per-item/default behavior.

**Sprint and review resources.** The owner-only `product.sprint` create/note commands accept optional `attachments` with the same validation as task creation. Saved sprint and conversation projections retain their bytes; old records without the field remain valid. The auxiliary planner receives ordinary ACP image/embedded-resource blocks, not serialized base64 prose. Its cumulative input shares the eight-file/4-MiB bound, checked before saving a note. Review add/edit comments retain optional attachments; sending comments forwards their combined resources through `executions.prompt` before marking comments sent. Queue edits preserve attachments when omitted and replace them when supplied. Conflict-resolution guidance carries attachments through the same prompt route. `product.read {taskId, attachments:true}` returns only the selected task's saved creation bytes for on-demand read-back, without enlarging board DTOs. Product-state saves refuse explicitly before exceeding the frame budget.

**Limits, version 1.** 50 task summaries per page; 100 events or history rows per page; 64 KiB of content per response page; 8 MiB per local JSON frame; 32,000 characters per description or answer; request identities of at most 128 characters. Oversized content is marked unavailable or delivered through bounded text pages; it is never silently truncated.

**Version.** The public wire version is 1.8 (prior fingerprints remain in the lock), independent of the product version and of ACP protocol version 1. The schema is canonical JSON Schema 2020-12 with a committed fingerprint. Commands are strict; responses may add fields.
