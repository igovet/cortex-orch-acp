# Remote access and push

**Status: remote access is built and not qualified. The desktop machine service embeds an iroh host (`crates/workspace-remote`), the desktop has a Settings, Remote access page, and an Android app (`apps/cortex-workspace-android`) pairs with and drives paired machines. A self-hosted relay stack exists in `deploy/relay/`. Checked only by no-paid automated tests on loopback and one debug APK build; not verified: anything on a physical Android device or emulator, a connection through a relay, pairing between a real phone and a real desktop, and the desktop page in the native window. Not implemented: the push gateway and FCM push (the phone raises its own notifications instead; see [phone notifications](#phone-notifications)), Android Keystore wrapping of the device key, an app lock, a phone-side relay override, desktop-to-desktop remote machines (the desktop's Add remote machine control stays disabled with its reason).**

A machine means a running Cortex Workspace process containing projects, not a project or client device. The desktop has one local machine. The Android app has no local machine: it connects only to remote machines that were paired from a desktop. The desktop's own Add remote machine control (desktop to desktop) is not built.

## Host (the computer)

The machine service starts the host with the service. Remote access is **off by default**, the switch persists across restarts, and while it is off no endpoint is bound. Only the local owner (the desktop window on the service's Unix socket) can use the `remote.*` methods: `remote.status`, `remote.enable`, `remote.pairing.start`, `remote.pairing.cancel`, `remote.pairing.decide`, `remote.devices.revoke`, `remote.relay.set` and `remote.sudo.set` (whether a paired phone may send a sudo password or a sign-in token, the "Passwords and tokens from phones" switch; on by default, kept in `askpass.json` in the service's state directory). A paired device is refused every `remote.*` method.

- **Identity.** The machine's iroh identity is a 32-byte key in `remote-host.key`, a 0600 file in the `remote/` folder of the service's private state directory, next to the paired-device registry and the remote settings. Private files are opened without following links and are refused, not repaired, when another user owns them or group or other permission bits are set. The key is a file, not an OS keyring entry (see Current limits).
- **Network.** When remote access is on, the service binds an iroh UDP endpoint on all addresses, on the last port it used. The endpoint uses no n0 public relay and no n0 address lookup. The relay is either none (direct addresses only, which works on the same network) or exactly one configured relay. The built-in default relay is read at build time from `crates/workspace-remote/default-relay.txt`; it is `https://cortex-relay.vetrov.dev`, so a machine with no override offers that relay beside its direct addresses. A per-machine override set on the Remote access page takes precedence and can be cleared. Changing the relay while remote access is on rebinds the endpoint, which closes current connections and cancels an open pairing offer.
- **Pairing.** The owner starts a pairing on the desktop. It produces a single-use pairing link (`cortex-pair:` followed by an encoded host identity, a 32-byte secret, the machine name, the relay if any and up to eight direct addresses, with a checksum), shown as a QR code and as copyable text. The link is valid for 5 minutes; five wrong secrets cancel the pairing. When the phone presents the correct secret, both sides show a fingerprint derived from both identities and the secret, and the desktop shows a pending request with Allow and Deny. Only Allow stores the device. Nothing about the machine beyond the pairing status is sent before Allow. There is no short pairing code.
- **Revoke.** Revoking a device removes it from memory and closes its connections at once, then rewrites the registry; a failed write is reported and does not restore access in this session: the device stays as a disconnected row that grants no access, and after repairing storage (for example file permissions) pressing Revoke again for the same device persists the removal and clears the row. Restarting before a successful retry can lose the revocation. Turning remote access off closes every connection and cancels pairing. Allow likewise stores the device first: if the save fails, the phone is told `cancelled` and nothing is added; a private grant-intent file (`remote-grant.json`) lets the next start remove a provisional device whose save was uncertain before binding, and if that rollback fails remote access stays off until storage is repaired. A damaged registry or key file keeps remote access off and is not overwritten.
- **Version probe.** A third ALPN, `cortex-workspace/version/1`, lets a client that failed to connect tell an incompatible machine from an unreachable one; it returns protocol constants only ([protocol](protocol.md#remote-transport-and-version-refusals-built-not-qualified)). The phone then shows "update needed".
- **Tunnel.** A paired device's connection is authenticated by its endpoint identity through iroh's TLS handshake, independent of the relay. Each remote stream is bridged to one fresh connection to the machine service's local socket. Before a request is forwarded, it is parsed and passed through a closed allowlist ([security](security.md#remote-access-built-not-qualified)); a refused request is answered with `remote_operation_refused` and never reaches the service. A malformed or oversized frame resets the stream. Bounds: at most 8 devices connected, 2 connections and 16 streams per device, 4 pairing connections at once.

The desktop page (Settings, Remote access) holds the switch, the QR code and copy-link control, the pending request with Allow and Deny, the paired devices with Revoke, the relay setting and the "Passwords and tokens from phones" switch (formerly "Sudo passwords from phones"; the stored setting is unchanged). It is covered by interface tests; it has not been looked at in the native desktop window.

## Phone (Android)

The Android app is the same interface as the desktop in its phone shell ([screens](SCREENS.md#phone-shell)). It scans the QR code with the Tauri barcode-scanner plugin or accepts a pasted pairing link, shows the fingerprint and waits for the desktop's Allow. The phone's device key is a 0600 file in the app's private data; the APK build switches Android backup off so the key is not backed up. The app's native command set is closed, and a request from its interface passes the phone profile of the shared request allowlist (`crates/workspace-client`) before it is sent, then the machine's own allowlist. Its relay comes from the pairing link; the phone has no relay override. See [platforms](platforms.md#android-build-prerequisites) for building it.

When a task's command on the machine asks for a sudo password, the phone shows the same "Password for sudo" card as the desktop ([screens](SCREENS.md#sudo-password-prompt)); its password crosses the paired, end-to-end encrypted connection (through the relay only as ciphertext), goes to sudo once and is not stored. With "Passwords and tokens from phones" off, the phone can only cancel a prompt.

When a task lacks access (a GitHub, Codex or Claude sign-in, or sudo), the phone shows the same owner action card as the desktop ([screens](SCREENS.md#owner-action-card)) through `owner_actions.list`. It can ask the machine to check again and dismiss the card. It cannot open the sign-in in the desktop's terminal (both allowlists refuse `owner_actions.act` with `terminal`), so it shows the login command to run on the computer. It can paste a GitHub token only while "Passwords and tokens from phones" is on; the token crosses the encrypted connection, goes to `gh auth login --with-token` on the machine once and is not stored ([security](../../SECURITY.md#owner-actions-sign-ins-and-pasted-tokens)). With phone notifications on, a new card raises "Task needs access".

A connection-lost band shows when the machine cannot be reached; a retry reconnects without replaying an action. The workstation must be running, remote access must be on, and an available path (same network, or the relay) must exist. There is no guarantee of universal connectivity.

## Relay

The relay is one self-hosted `iroh-relay` service on the owner's own server ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md)). It forwards only ciphertext. The n0 public relay is not used and cannot be enabled by the built code ([CW-N05](backlog/CW-N05.md)). The deployment is in `deploy/relay/` ([self-hosted services](self-hosted-services.md)). No relay is deployed or verified from this repository, and no connection through a relay has been tested.

## Phone notifications

The Android app raises its own notifications for every paired machine; no push service is involved. While **Phone notifications** is on in the phone's Settings (on by default once a machine is paired), a foreground service (Android's `specialUse` type) shows one quiet "Connected to your computers" notification and keeps the app's process, and so its encrypted connections, alive in the background. Over each paired machine's connection the phone holds a read-only `notifications.subscribe` stream: the machine sends its open owner moments (the same ones the desktop notifies about) as one set at once and after each change, each with its kind, an opaque fingerprint, the task or sprint title and the place to open. The phone raises a notification for a moment it has not announced before, on one of three channels (Needs your answer, Results ready, Failures), replaces it when the same task moves on, and withdraws it when the moment is gone. Reconnecting and restarting the app announce nothing twice; the first set after pairing only records what is already open. A tap opens the app on that machine at that task, question or sprint, through the same path as a desktop notification click. Turning the setting on asks Android for the notification permission; Settings shows when Android blocks notifications and offers Android's battery optimisation list, since a phone that optimises the app may pause the connection while it sleeps. What crosses the connection and what the phone checks is in [SECURITY.md](../../SECURITY.md#phone-notifications) and [platforms](platforms.md#android-phone-notifications). Checked by no-paid automated tests only: background and Doze behaviour, the permission prompt and a tap on a physical phone are not verified.

## Push (planned)

FCM push is not needed for the notifications above. A later Android release may still target FCM push through a push gateway that runs as a self-hosted container on the owner's server ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md)). The gateway is a stateless forwarder: it holds the FCM sender credential as a Docker secret file, authenticates desktop callers, rate-limits them, and forwards metadata-only wake-up signals (a closed set of event types and opaque references, never task content). For valid requests it transiently receives a recipient token and the closed metadata payload, never task content; it does not persist tokens or payload bodies. Requests containing content fields are rejected, and their bodies are not logged. How the gateway authenticates desktop callers is an open owner decision ([risks](risks-and-open-decisions.md)). On open, the app fetches authorized content over the authenticated channel. Token registration, rotation, duplicate notifications, delivery delays and revoked devices need tests. FCM delivery is not guaranteed; show unavailable on devices lacking supported services or permission, and recover via normal reconnect. Neither the push gateway nor any push code exists. Deployment, secret handling, TLS, health checks and rollback are described in [self-hosted services](self-hosted-services.md).

Pairing and data traffic use embedded iroh, not a Cloudflare Tunnel. A tunnel needs a persistent hostname tied to a Cloudflare account and domain, terminates TLS at Cloudflare (so end-to-end encryption and QR pairing would still be required on top), and does not solve push: Android stops background sockets, and the FCM sender credential cannot be shipped in the desktop app. See [ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md) and the superseded [ADR 0010](adr/0010-push-gateway-cloudflare.md).

## Current limits

- Keys are 0600 files (the machine's in the service's state directory, the phone's in the app's private data). They are not wrapped by the OS keyring or the Android Keystore; code running as the same user, or a rooted phone, can read them.
- No app lock, FCM push, phone-side relay override, terminal or file editing on the phone. Code is read-only there.
- A paired phone is trusted with the machine's work and settings ([security](security.md#remote-access-built-not-qualified)); it is not a view-only client.
- Not verified: every item named in the status line. No platform is qualified for release.
