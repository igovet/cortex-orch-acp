# Remote access and push

**Status: planned; no implementation or qualification is implied.**

A machine means a running Cortex Workspace process containing projects, not a project or client device. One local machine is present at launch; a remote machine is connected via the server connector. The switcher selects one machine at a time; Inbox and Archive aggregate across machines. This is planned, not a claim that remote machine integration is implemented.

Planned embedded iroh transport: local discovery when available, direct QUIC across networks where possible, and an iroh relay as fallback when a direct connection fails. The relay forwards only ciphertext and must not receive project plaintext. The relay is one self-hosted `iroh-relay` service on the owner's own server ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md)). The n0 public relay is not used by default; it stays disabled unless the owner records a trust decision ([CW-N05](backlog/CW-N05.md)). Embedding avoids a separate VPN installation. Relay availability, NAT behavior, Android integration, operational cost and actual end-to-end protection must be qualified; no guarantee of universal connectivity. The workstation must be running and reachable through an available path.

Planning assumption to confirm: `iroh-relay` is a native Rust server and cannot run on Cloudflare Workers. It is therefore deployed as a container, not on Workers.

Pair through a QR enrollment containing host identity, relay information and a short-lived one-use secret, followed by local desktop confirmation. Persist host and device keys securely; revoke and terminate existing sessions; provide a safe host-key rotation/re-enrollment procedure. Reconnect across Wi-Fi/cellular transitions with cursor resume and gap detection. The app ships with the owner's relay and push gateway URLs as built-in defaults. The user can override them and installs nothing extra.

The Android release, which follows the Ubuntu desktop first release, targets FCM Android push through a push gateway that runs as a self-hosted container on the owner's server ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md)). The gateway is a stateless forwarder: it holds the FCM sender credential as a Docker secret file, authenticates desktop callers, rate-limits them, and forwards metadata-only wake-up signals (a closed set of event types and opaque references, never task content). For valid requests it transiently receives a recipient token and the closed metadata payload, never task content; it does not persist tokens or payload bodies. Requests containing content fields are rejected, and their bodies are not logged. How the gateway authenticates desktop callers is an open owner decision ([risks](risks-and-open-decisions.md)). On open, the app fetches authorized content over the authenticated channel. Token registration, rotation, duplicate notifications, delivery delays and revoked devices need tests. FCM delivery is not guaranteed; show unavailable on devices lacking supported services or permission, and recover via normal reconnect. Deployment, secret handling, TLS, health checks and rollback are described in [self-hosted services](self-hosted-services.md).

Pairing and data traffic use embedded iroh, not a Cloudflare Tunnel. A tunnel needs a persistent hostname tied to a Cloudflare account and domain, terminates TLS at Cloudflare (so end-to-end encryption and QR pairing would still be required on top), and does not solve push: Android stops background sockets, and the FCM sender credential cannot be shipped in the desktop app. See [ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md) and the superseded [ADR 0010](adr/0010-push-gateway-cloudflare.md).

No relay, push gateway, credential or physical delivery has yet been deployed or verified.
