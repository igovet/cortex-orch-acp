# Security design

**Status: security design. The local desktop slice implements the local trust boundary below; its different-OS-user check is unverified. Remote access is built and checked only by no-paid automated tests (see its section below); it is not qualified, and nothing was verified on a physical device or through a relay. Push is planned and not implemented.**

Pair a device with an expiring single-use enrollment secret and explicit local confirmation, binding a device key to a limited grant. Keep secrets in OS-protected storage; never log tokens, source contents, prompts or private keys. Revoke immediately, close active sessions and reject future operations. Authenticate both peers independently of relay location. Apply authorization to every request; remote terminal and Git carry real execution authority.

Restrict project paths and defend against traversal, symlink escapes and private-path access. The packaged units root the service at `/`, because a same-user service gains nothing by limiting the owner to their home and owners keep repositories on other disks. A project is a folder the owner can write to, resolved to its real path once at registration and checked as symlink-free on every later use; the channel's private state and runtime directories and any `.cortex` or `.cortex-dev` path stay refused. Local Code saves need a runtime-confirmed [file lease and matching disk revision](ide-and-git.md#code-editing-and-write-leases); this is cooperative exclusion, not an OS lock or a visual pause. Treat push as an opaque notification hint, not an authority to execute commands.

## Local slice trust boundary (built)

The machine service listens only on a Unix domain socket in a private per-user runtime directory. The directory is mode 0700 and the socket 0600; both ends compare the peer's effective user with their own, and a mismatch is refused. The service's own private folders (that runtime directory and, in the dev channel, the config, state, cache and data folders it gives started processes) must be real directories owned by the current user; one that is merely too permissive (0775 under the user's own group, 0755) is made 0700 in place, while a world-writable, other-group-writable or foreign-owned folder stays refused with a message naming the folder and the problem. The service opens no TCP, loopback HTTP or WebSocket listener. The one network listener it can open is the iroh UDP endpoint of remote access, bound only while the owner has turned remote access on (off by default; see [Remote access](#remote-access-built-not-qualified)). The actor of every request is derived from the authenticated peer; client-supplied actor values are replaced.

The desktop shell has one main window that loads only bundled local content. Its content security policy allows connections only to Tauri IPC, and it blocks frames, objects, forms and remote scripts. Media plays only from in-memory `blob:` URLs, so Code's file previews (pictures, video, sound, sanitized HTML and image-only SVG) load nothing remote and run no script; see [viewing files](local-task-execution.md#viewing-files). It grants no shell, filesystem or process capability and exposes a closed request command plus a bounded notification command. Native notifications use the fixed session-bus Notify method, a generic title and markup-escaped work label; no question body or executable is accepted. The machine service raises the desktop notifications on the owner's session bus and keeps each one's closed, validated target (a task, sprint or question by id); only a default-action click on an id it raised sends that target to the windows, and the desktop shell claims it to receive the activation token. With no window open, the service starts the desktop app through `systemd-run --user` with that token and nothing else. The window resolves a target against what it knows. A click carries no data of its own (see [SECURITY.md](../../SECURITY.md)). Because the window draws its own frame, the main window alone may also minimize, maximize, close and start dragging itself, and read whether it is maximized; these five permissions act only on that window. External navigation and new windows are refused. A separate, main-window-only result-link command accepts bounded HTTP(S) and mail addresses or absolute local file paths from explicit activation. It cannot take a command or executable name. Opening a video or subtitle file from a result requires a second click in the path popup; the resolved target must be a regular, non-executable file of a supported type. The requested and resolved paths must both avoid `.git` and marked Cortex stores. A `.cortex` or `.cortex-dev` ancestor is checked for `cortex.sqlite3`; a Dev ancestor is also checked for `owner.json` inside it or the legacy `.cortex-dev-owner.json` beside it. If a marker cannot be checked, the handoff is refused. It is handed off as one argument to the fixed system opener, not read into the webview. See [Result links](local-task-execution.md#result-links).

The ACP child runs with a cleared environment. The dev channel points the child's XDG directories at dev-only paths and does not change `HOME` or copy account files. Prompts, transcripts, question text and result bodies are not copied into the public invalidation journal.

The package installs the complete channel-owned runtime, the locked Codex/Claude dependency tree and checksum-verified Node, plus a login-start symlink. Engine discovery prefers the channel's own root-owned bundle. The Codex private patch remains under connection state; the package tree is never patched. Native logins are referenced in place, never copied. See the [licence inventory](../project/bundled-engine-licenses.md) for the owner's 2026-11-06 distribution-risk decision, not Anthropic permission. Native startup uses bounded, fixed `/usr/bin/systemctl --user` reload/start calls; the webview has no arbitrary process interface. Minimal maintainer scripts reload and try-restart active users' matching units on upgrade and stop them on removal, best effort, without changing user data or Paseo. Old `service.env` files cannot redirect the bundled runtime. Bubblewrap remains required; the package does not disable AppArmor restrictions or introduce a privileged sandbox helper.

Machine facts and owner actions run through the native machine host (`crates/workspace-service/src/machine`, in the service process; the former Python helper `machine_tools.py` was removed on 2026-11-16). The webview names only an operation from a closed set checked by the bridge and again by the service, a registered project, and parameters. It never supplies a root, a state directory, a command or an executable: the service resolves those. The host refuses a path that is absolute, contains `..`, starts in `.git`, `.cortex` or `.cortex-dev`, or resolves outside the checkout through a link. An owner save goes further: it refuses `.git`, `.cortex` and `.cortex-dev` at any depth, walks to the file one folder at a time with `O_NOFOLLOW` so no link on the path is followed even inside the checkout, is bounded to 512 KiB of UTF-8 text with no NUL byte, writes only over the revision the owner read, and needs a live per-file [owner write lease](ide-and-git.md#code-editing-and-write-leases). The lease is cooperative: it excludes the same project's structured worker file tools and other Code saves, while host commands, outside writes from other projects, native engine writes, Git and external editors are outside the guarantee, and the revision check still protects the save. See [editing files](local-task-execution.md#editing-files). Git runs from fixed argument lists with prompts disabled, a push never forces, and a credential embedded in a remote URL is removed before the URL is reported. Discarding work and deleting need an explicit confirmation in the request. Cortex settings go through the configuration management API with its revision checks, so a stored MCP secret is never read back. Task facts and worker activity are read from the project store through Core's non-initializing read-only mode; the only store writes caused by owner actions are Code's lease and save transactions, which go through Core. The separate owner terminal boundary below intentionally grants interactive shell authority; it is not routed through this helper.

### Local dictation (built, local Linux)

Only bundled main-window content may call voice.start/read/stop/cancel; the
same-user socket and shared Rust parser enforce the closed identities and refuse
audio, file paths, URLs, commands, environments and send flags. A random session
identity binds reads and controls; recent start identities do not restart capture.
There is one microphone lease, refreshed by reads and cancelled after ten seconds
without a read. Stopping finalizes a preview and cannot send anything.

The service starts its fixed packaged worker with a cleared environment, retaining
only HOME, LANG and the actual desktop XDG_RUNTIME_DIR for local audio access.
It uses the bundled Node and fixed parec capture arguments. No project, engine,
credential environment or webview-selected executable is passed. The helper
downloads only the committed model URL, checks the exact size and SHA-256 before
extracting named model members, verifies their hashes and caches them under the
channel's private state directory. Audio stays in bounded process memory; transcript
snapshots are local IPC only, never public journal/status logs. A recording stops
at 90 seconds. Cancel, service stop and lease expiry kill the owned worker/capture
process group and reap the worker. Abrupt service death has no guarantee of reaping
descendants beyond the helper's parent-death signal; same-user code is trusted.
This is local microphone authority, not hostile-code isolation.

### Separate worktree boundary

The runtime resolves the authenticated checkout binding, not a client path or
branch guess. Native engine sessions use a read-only checkout view. Scoped file
tools are the write path; they exclude sibling checkouts, the main project folder,
private stores and Git control paths. Brokered commands and verification use a
read-only checkout and Git metadata, private writable scratch and no network.
They refuse an outside cwd, privilege escalation and unisolated host reroutes.
External MCP and OpenCode routes are unavailable in this mode; an unsupported
view refuses rather than running unconfined. This is checkout separation and
constrained effects, not hostile-code isolation. In particular, the engine view
is distinct from the no-network command view. Owner Git actions and the terminal
are not model command privileges.

### Owner terminal (built, local Linux)

Ctrl+J opens one service-owned PTY per registered project, including from its task views. The displayed project folder is the initial cwd, not a task worktree. The service selects the user's executable shell (native SHELL/password-database fallback), passes only the fixed interactive flag and TERM=xterm-256color, and runs as the same OS user with that user's service environment. It does not activate Cortex or a model. The webview cannot choose an executable, cwd, environment, command argument list or one-shot execution operation.

Only bundled main-window content can call terminal.open, terminal.read (output only), terminal.write, terminal.resize and terminal.close through the existing same-user Unix socket. The Rust request types reject unknown fields and invalid identities, dimensions or sizes in both the native bridge and service. Every request binds a registered project; subsequent operations also bind its unpredictable session identity. Unknown/removed projects and lost sessions are refused. Opening an existing project PTY reattaches, never restarts a command. The initial directory is rechecked, including dev-store ownership and canonical-path equality.

This is deliberate **owner shell authority**, not a sandbox: typed shell input can execute programs, change cwd, access the user's files/accounts and network, or change production data. A compromised trusted webview has that same terminal authority. The closed operations prevent a second generic process API, not shell execution through input. Terminal bytes never enter the public journal or service status log; only a bounded in-memory tail is retained.

There are at most eight sessions (one per project), 64 KiB retained output per PTY, 16 KiB per output page, 4 KiB per input write and a 16 KiB client input queue. Dimensions are 2–500 columns and 1–500 rows; browser scrollback is 1,000 lines. Nonblocking master IO and bounded drain work prevent slow input/output from creating unbounded service queues. A dropped tail is explicit. Short writes and uncertain deliveries are not replayed. The UI stops input on failure and offers explicit reattachment; it never resends prior input.

Hiding or closing the window detaches only. Explicit Close shell, project removal and orderly service stop terminate the PTY's dedicated session process groups: SIGTERM, 150 ms grace, then SIGKILL, followed by shell reaping. Foreground and background job groups are included. The shell PID is retained until cleanup to prevent identity reuse. A service restart has no terminal history or command replay. Abrupt service death, intentionally daemonized jobs that leave the session, shell resource consumption and hostile same-user code are not contained by this cleanup mechanism; there is no CPU, memory, filesystem or network sandbox for the owner's shell. Remote terminals (the remote-access allowlist refuses every `terminal.*` method), task/worktree-specific PTYs and GPU addons remain unimplemented; the pinned xterm.js 6.0.0 DOM renderer and fit addon 0.11.0 use theme tokens and the bundled monospace font.

Dev uses `.cortex-dev` beside release/default `.cortex`, without opening, importing or migrating release data. Registration reserves `.cortex-dev-owner.json`; activation binds the exclusively created dev directory by device/inode. An unowned or changed dev store is refused, not a folder merely containing release data. Older markers/data are left untouched; a project an older build activated is reserved at activation only while no `.cortex-dev` exists. One store per logical project per channel is shared by linked worktrees ([CW-S12](backlog/CW-S12.md)).

Limits: the same OS user is local trust, not isolation from hostile code running as that user. The different-OS-user connection check is not yet verified. The push gateway runs as a self-hosted container on the owner's server ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md)). It holds the FCM credential as a Docker secret file, authenticates desktop callers, rate-limits them and rejects any payload with fields beyond the closed schema. Its logs must contain no task content, payload body or full token. The FCM credential and caller-authentication keys stay outside git and are absent from client builds. The existing [ACP boundary](../../SECURITY.md) remains authoritative for current behavior.

Server-side trust boundary: the owner's server runs the relay and the gateway, and it is internet-reachable. Its compromise would expose the FCM credential, allow abuse of the gateway, and expose relay metadata. The relay can be given an access policy (allowlist, shared token or HTTP callout), but device authorization still rests on the desktop (CW-N04) and never on the relay. Threat-model relay compromise, gateway compromise, server compromise, secret-file leakage, stolen devices, key rotation and malicious projects before implementation.

## Remote access (built, not qualified)

Remote access lets a paired phone drive the machine service. It is built in `crates/workspace-remote` (the iroh host and client), `crates/workspace-service/src/remote.rs` and `remote_policy.rs`, and `crates/workspace-client`. It has no-paid automated checks only: loopback integration tests, policy unit tests and one end-to-end test through a real service. Not verified: a physical Android device or emulator, a connection through a relay, pairing between a real phone and a real desktop. See [remote access](remote-access.md) for the flow.

- **Off by default.** No endpoint is bound until the owner turns remote access on at the machine; the choice persists. Only the local owner's window, over the Unix socket, can use `remote.status`, `remote.enable`, `remote.pairing.*`, `remote.devices.revoke` and `remote.relay.set`.
- **Identity.** The machine has one iroh identity, a 32-byte key in a 0600 file (`remote-host.key`) in the `remote/` folder of the service's private state directory. Each phone has its own key, a 0600 file in the app's private data, with Android backup switched off by the build. Private files are opened without following links and refused if another user owns them or group or other bits are set. At rest the keys are files: not wrapped by an OS keyring or the Android Keystore (not implemented), so code running as the same user, or a rooted phone, can read them. Peers authenticate each other by endpoint identity in iroh's TLS handshake, independently of the relay.
- **Pairing.** One pairing offer is open at a time; starting another replaces it. A single-use link (`cortex-pair:`, shown as a QR code and copyable) carries the machine identity, a 32-byte secret, the machine name, the relay if any and direct addresses. It expires after 5 minutes; the fifth wrong secret cancels it; the secret is compared in constant time and a used secret is consumed. After a correct secret, both screens show a fingerprint derived from both identities and the secret, and the desktop shows a pending request with Allow and Deny. Only Allow stores the device; the owner is expected to compare the fingerprints. Nothing about the machine besides pairing status is sent before Allow. There is no short pairing code. The link holds the pairing secret while valid, so it must be shared only with the phone being paired.
- **Device registry.** Allow saves the device before the phone is told `allowed`. If the save fails, nothing is added, the owner's decision returns `remote_state_unavailable` and the phone is told `cancelled`. Before the registry write the host records a private grant-intent file (`remote-grant.json`); if the save is uncertain, the next start removes the provisional device before binding, and if that rollback fails remote access stays off (no endpoint bound) until storage is repaired. A registry or key file that cannot be parsed is reported as `remote_state_corrupt` (not as a permissions problem): remote access stays off, no endpoint is bound and the file is not overwritten.
- **Revoke.** Revoking a device removes it from memory and closes its connections at once, then rewrites the registry. If the write fails, the error is returned and access is not restored in this session; the device stays visible as a disconnected row that grants no access. Repair storage (for example file permissions) and press Revoke again for the same device to persist the removal and clear the row. Restarting before a successful retry can lose the revocation, because the file may still list the device. Requests already handed to the local service are not rolled back or replayed, so their outcome is unknown. A device that is not in the registry has its RPC connection refused; pairing and the constants-only version probe (which reveals no device or machine data and grants no access) are the only exchanges open to it. Turning remote access off closes every connection and cancels pairing.
- **Version probe.** Besides `cortex-workspace/pair/1` and `cortex-workspace/rpc/1`, the host serves `cortex-workspace/version/1`. One request byte gets one bounded JSON reply of protocol constants only (`{"supported":[...],"wire":"1.10"}`), then the stream closes. It reveals no machine name, identity-derived data, device list, pairing state or relay address and is not an authorization; it counts against the 32-handshake limit and the 10-second timeouts. A client tries it only after a failed pairing or rpc dial: a reply that lacks the requested ALPN becomes `remote_incompatible_version`; otherwise the machine is reported unreachable. An unknown pairing-link format is refused locally as `unsupported_pairing_link_version`.
- **Allowlist.** Every tunnelled stream is bridged to a fresh connection to the same local socket and credentials the owner's own window uses, so the allowlist in `remote_policy.rs` is the only place a remote request is refused. It is closed and fail-closed: a method or machine operation not listed is refused, including every method added later until it is classified. A refused request gets `remote_operation_refused` and is not forwarded; a malformed or oversized frame resets the stream. The phone app applies its own stricter profile first (`crates/workspace-client`), so a refusal at the machine is a second gate, not the only one.
  - Allowed: service status, capabilities and subscription; project list, register, rename, remove, activate and status; folder search; native task queries and boards; the workspace read; execution cancel, prompt and control; and `machine.call` operations for the machine overview, workflow description, diagnostics and cleanup, machine and project settings read and save, configuration actions and MCP discovery, repository snapshot, context, file read, list and skills, workers, and tasks, sprints, results, history, messages, comments, owner integration and attachments. Within those, an engine connection may only be rechecked or given an API key, and maintenance may only read status, check, cancel, or start a clone or download job. Open sudo password prompts may be listed (`askpass.list`) and cancelled; one may be answered with a password (`askpass.answer`) only while the owner's "Passwords and tokens from phones" setting is on (the default). That password then crosses the paired, end-to-end encrypted channel ([SECURITY.md](../../SECURITY.md#owner-password-for-sudo-askpass-and-host-rerouting)). Open owner actions may be listed (`owner_actions.list`), checked again and dismissed; a GitHub sign-in token may be sent (`owner_actions.act` with `token`) only under the same setting, and the desktop terminal login (`terminal`) is refused ([SECURITY.md](../../SECURITY.md#owner-actions-sign-ins-and-pasted-tokens)).
  - Refused: every `remote.*` method (including `remote.sudo.set`, which changes that setting), `service.stop`, every `terminal.*` and `voice.*` method, file saves and new files in a checkout, every Git write action (commit, stage, revert, push, pull, fetch, branch, drafts, worktree deletion) and Git initialisation, folder-opening and absolute-path operations meant for the desktop's own openers, native engine login, installing or rolling back a package or acknowledging an unconfirmed install, and any unknown method or operation.
- **Relay.** The endpoint never uses an n0 public relay or n0 address lookup. A relay is either none (direct addresses only) or the one configured relay. Traffic is encrypted end to end between the two devices; a relay sees which endpoint identities connect, when, how much data moves and client IP addresses, and cannot read content, impersonate a device or decide which device may control a machine. Device authorization rests on the desktop's registry, never on the relay (`deploy/relay/` runs it with `access = "everyone"`; an allowlist is optional).
- **Bounds.** At most 8 paired devices connected at once, 2 connections and 16 streams per device, 4 pairing connections and 32 handshakes in progress; frames are bounded by the service's frame limit.

Honest limits:

- A paired phone has command execution authority on the machine, although it has no terminal. It can send prompts to executions, start and steer work, change machine and project settings (including MCP server configuration that the service later runs), register or remove projects, and perform owner integration actions. It is not a view-only client. Whether settings writes from a phone should be narrower is an open review item ([risks](risks-and-open-decisions.md)).
- Remote devices cannot write files or Git state directly, but work they start can.
- The allowlist and pairing flow are not qualified: no review by a second party, no device run, no relay run.
- Nothing restricts which networks can send UDP to the bound port; protection is the iroh handshake and the paired-device check.
- The phone has no app lock. Anyone holding an unlocked paired phone has the phone's authority. A revoke at the computer is the remedy.
- The push gateway does not exist; the push rules in the design above remain a plan.
