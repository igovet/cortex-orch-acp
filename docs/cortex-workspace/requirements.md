# Requirements

**Status: each requirement carries its own status, checked against the code: Implemented, Partly implemented, Not implemented or Not confirmed in code. "Implemented" means the behavior exists in source and is covered by no-paid automated checks. No requirement is verified by a paid live run, a real Ubuntu desktop session or a published release, and none is release-qualified.**

A result with any open or failed check is not accepted automatically; the queue sends it back to the agent when it can be repaired, and otherwise pauses with one owner decision pinned in the task's conversation. | CW-R42 | Development and release are isolated channels. Dev refuses only an unowned or changed dev store; it never adopts or migrates the release store. | Implemented: isolated dev and release channels with separate packages, stores and services; the release channel is not published; see [platforms](platforms.md) |

## Owner decisions (2026-11-05)

- Gate D passed for the clickable prototype ([desktop approval](design/desktop-approval.md)). Gate M remains open.
- Attachments by drag and drop and by paste in the composer and the free-form answer field: CW-R39.
- Automatic sprint: a checked task moves to Ready to merge by itself, and the owner confirms there: CW-R20. Since 1.0.6 the system records that task's acceptance, marked as automatic, when its result passes the manual Accept rules. Superseded for Automatic sprints by the decision of 2026-11-19 below.
- Sprint run modes (2026-11-19): a sprint runs in Manual, Hybrid or Automatic mode. Hybrid is the former automatic mode: the queue runs by itself and the owner confirms each merge. Automatic runs tasks to Done on the current branch by themselves; the owner answers only questions about the work and permission requests, and confirms only a different target branch. Stored sprints of the former automatic mode open as Hybrid with unchanged behavior. Details: [local task execution](local-task-execution.md#sprint-run-modes) (CW-R18, CW-R20).
- Check recovery, forced re-run, and acceptance with an unpassed check only for a technical blocker: CW-R40.
- Orchestration settings rework, requested after Gate D: field-level parity with the Cortex configuration exposed in Paseo, editable MCP servers, and per-tool access shown for the tools a connected server lists. This extends CW-R23 as CW-R41. The planned sections and shared rules are in [SCREENS](SCREENS.md#orchestration-settings-desktop); acceptance criteria are in [CW-U07](backlog/CW-U07.md) and [CW-C01](backlog/CW-C01.md). On 2026-11-19 the owner decided that these settings follow the structure and the way of configuring of the Paseo settings panel, and chose to implement without a mockup approval step.
- Native builds run in a Docker container. The host needs no development packages, and the owner does not install system libraries for the build. This replaces the earlier statement that the owner installs them (CW-S09, CW-S11, CW-F01).
- Dev and release channels are isolated. A local build is the dev channel, and manual GitHub Actions runs publish production from `main` and dev prereleases from `dev`: CW-R42, implemented by CW-S12, with the release workflow in CW-S11 and the update rule in CW-U16.
- Installing the `.deb` must provide Cortex and its services without a source checkout, manual `service.env` or a settings-clone prerequisite. Login startup, bounded native app-driven start, best-effort upgrade restart and removal stop apply to both isolated channels. This supersedes the earlier explicit-checkout-only and never-activate-units rules.
- Open, not decided: per-tool engine access, and access per worker role (for example, only frontend and QA workers). The current configuration schema stores neither.
