## Native read-path diagnostic (2026-11-11)

On the reference Intel Core i5-14600K (20 logical CPUs), Linux 7.0.0-42,
Rust 1.99.1 debug test build and Python 3.12.13, a disposable format-12 store
contained 1,000 saved tasks (one bound RECOVERING execution) and 100,000 retained
history update rows. No owner store or running application was opened.

The executable experiment is
`cargo test --locked -p cortex-core --test read_latency -- --ignored --nocapture`.
It alternates 10 warmups and 100 measured calls per route on the same fixture.
The old route is a persistent Python stdio child calling the real WorkspaceAPI;
its startup is excluded. Native measures the reusable Rust provider plus reply
serialization, **excluding service socket, Tauri, UI rendering and polling delay**.
This is not a like-for-like desktop end-to-end speedup or a release gate.

| Read | Python p50 / p95 / p99 ms | Native p50 / p95 / p99 ms |
|---|---|---|
| First 50-task page | 5.721 / 8.639 / 10.069 | 4.376 / 7.147 / 8.588 |
| Bound task detail/state | 1.576 / 2.245 / 2.770 | 0.292 / 0.523 / 0.695 |

The measured median reductions are about 1.3× and 5.4× respectively. The fixture
represents populated storage, not 1,000 simultaneously executing agents. History
content rendering and cold startup were not timed. Native task-page byte budgeting
is additive, avoiding repeated serialization of each growing page prefix.
The service currently polls opened Core readers every 250 ms; that delay is not
included above. Delta handling avoids a task-list or machine-facts refetch but
still rereads related bounded history/decision/result pages for changed tasks.
No installed desktop, rendered GUI, paid live run or zero-Python qualification
is established by these measurements.

## Cold board diagnostic (2026-11-11)

An authorized SQLite backup of a populated format-12 project was opened read-only:
2,864,820,224 source database bytes, 68 saved tasks, five executions, 703,052
runtime events and 52,726 host updates. Its two saved sprints had 36 and 31
members. The project task-page index was present; its first 51 identities took
0.032 ms in a Python SQLite probe. No migration, index installation or owner
store mutation was needed.

The shared Rust task-projection implementation read all 68 task DTOs (74,221
serialized bytes) in 8.548 ms. The former eager dependency, including full
conversation replay for all executed tasks, took 786.590 ms total, 32 history
pages and 2,667 visible rows on that same copy. This is a single diagnostic sample,
not p95, a physical cold-disk test, or process-launch-to-paint measurement.
It excludes socket, bridge, Python product/worker helpers and rendering.

The executable read-only diagnostic requires an explicit authorized database copy:

```sh
CORTEX_BENCH_COPY=/absolute/path/to/copy.sqlite3 cargo test --locked --offline -p cortex-core --lib copied_store_board_and_eager_history -- --ignored --nocapture
```

Batched native boards now separate placement and saved sprint membership from
conversation/worker enrichment. Existing bounded task pages remain available;
the board batch refuses more than 1,000 tasks or a reply above 768 KiB instead
of silently truncating membership. A persisted display-only board provides the
first view on subsequent launches; see [recovery](consistency-and-recovery.md#confirmed-board-on-launch).

## Idle and background work

With nothing changing, CPU is effectively zero; with work running, cost follows real updates.

| Work | When it runs | Bound |
|---|---|---|
| Project queues in the service | every 2 s the owning child compares file stamps of the store and the product record; a full pass runs only if they moved | no database connection while nothing moved; one full pass at least every 60 s, because project file changes announce nothing |
| Reading a result for the queues | once per task version, at most 60 s old | a finished or removed task's result is not read at all |
| Writing the product record | only when a pass changed it | an identical write would otherwise wake the next pass and every reader |
| Review actions in a product read | once per task version, at most 30 s old | kept in the machine's state directory; accepting a result still reads it fresh |
| Folder observation in a product read | one at a time per folder; reused for at most 30 s while the folder's change signal is unchanged | the signal is HEAD, the index entries, the identity, size and change times of every tracked and unignored untracked file, and the change times of the folder, of every directory holding such a file and of each untracked directory Git lists as a whole (four bounded Git listings and one `stat` per file and directory), so creating or removing an empty directory moves it; one bound remains: an empty directory created or removed inside a directory that holds only empty directories is not seen by the signal, so a product read can show the older digest for up to 30 s; a folder without Git, with a nested checkout, over 100,000 paths or with a file or directory changed in the last two seconds is observed fresh every time; accepting a result (manual or automatic), integration, check reruns and verification always observe fresh |
| Earlier-format folder digest in review actions | only for a result whose verification was recorded before its task was adopted by the native runtime, at most once per 30 s per folder, one at a time | a verification the native runtime recorded is compared with the native folder observation alone (a result it no longer matches is stale without walking the folder again); a product read reuses the last one while it is younger than 30 s, even if the folder changed since; a read that arrives while one is being taken gets the previous one without waiting if it is at most 60 s old, and otherwise waits for the running one; a folder not read for 60 s is forgotten; accepting a result, integration and reruns always take it fresh |
| Repository snapshot | per read | one at a time per project; reused for at most 30 s while the saved tasks' checkouts, baselines and retained integration sources, the commit drafts, every ref, the worktree list, the fetch marker, the origin URL and the folder change signal of every checkout (as above, taken for all checkouts at once) are unchanged, and no Git-changing command or owner Git action ran through the service since (each ends reuse at once); a checkout without a usable change signal makes the read fresh. Within a read each checkout's status and each distinct baseline diff is read once, however many saved records share it. A baseline diff is decided over the display limit (400,000 bytes) from the patches of the paths modified on both sides alone, read without rename detection and stopped at that limit; only otherwise is the full diff read, also stopped (its Git child killed) at the limit. Commit line counts are computed once per repository and commit (at most 4,096 commits for each of 32 repositories), only for commits not seen before, in up to eight parallel reads alongside the checkouts. A reused snapshot's relative commit times can be up to 30 s old |
| Code tree folder reads (`repo.list`) | on Code's open, its return to view, Refresh files and the owner's save there; one more read per folder the owner opens; never on a timer | one call carries the overview and up to 32 open folders. The overview is two `git ls-files --others --directory` reads (ignored, untracked) that never enter an ignored or untracked folder, at most 5,000 entries from at most 1 MiB of Git output; a folder read is one `readdir` of that folder alone, at most 500 entries shown of at most 100,000 looked at, and one `git check-ignore` for all listed entries. Ignored trees never enter the repository snapshot. Measured 2026-11-17 on this repository (about 1,540 tracked files and about 393,000 entries under ignored folders), in-process debug build, best of five: open 8.1 ms (20 overview entries, 1.3 KB), opening `target` 3.4 ms, `node_modules` 3.6 ms, `.workspace-build` 4.1 ms, `target/debug/deps` (3,365 entries) 19.2 ms for 500 shown and 2,865 counted (42 KB). Wall times of one test process, not of the installed app |
| Empty directories in a folder observation | with every observation | wholly Git-ignored directories (build output, dependency folders) are not entered, so a large checkout is walked in milliseconds; a walk over 300,000 entries outside ignored folders (or one that meets an unreadable directory) stops once, incomplete, and is not repeated; its digest then matches no other observation, so such a folder's results cannot be accepted until it can be observed in full; a failed listing of the ignored folders makes the folder unobservable instead of walking it another way; every observation, including verification and acceptance, uses the same rule, so their digests agree. Upgrading from a build that also counted empty directories inside ignored folders makes a result checked before the upgrade read as changed once, until its checks run again |
| Same-branch commit facts in a product read | per read | reused for at most 30 s while every ref, HEAD, the index, the recorded writes, the uncommitted paths and the recorded files themselves are unchanged; a recorded file changed in the last two seconds, or an inspection that reached its 4 s bound, is never reused |
| Ready-to-merge facts of a product read (`task_facts_presented.rs`) | one background inspection per folder at a time, up to three tasks at once | a screen's read (`defer`) never waits for it: it gets the last answer for an unchanged folder, every ref and the same task record (at most 30 s old), else the last answer marked `refreshing` (at most 60 s old), else a `pending` marker with the reason "Checking this task's files against its target branch…" and no commit offered; the window then makes one settling read, which waits for that inspection (at most 25 s) and has exactly what an inspection of the current folder says. Measured 2026-11-17 on an installed build before this change, cold (more than 30 s after the last read): `product.facts` took 0.07 to 0.37 s on projects with no task in Ready to merge, 11.6 s with four, 12.3 s with five and 26.7 s with eight, about 3 s per such task, and 2.0 to 2.7 s warm on the project with four; every read of any task in such a project, a task in review included, waited for it. Committing and merging inspect fresh |
| Folder observation of a screen's facts read | waited for at most 500 ms | a result whose check against the project folder is not known by then is shown from its own record (summary, version, runtime checks) with Accept off, the reason "Checking the result against the project…" and nothing else offered; the observation keeps running and the settling read that follows takes it over. Accepting a result still observes fresh |
| What a window reads in the background | only what a screen on view shows: a board, sprint or task page holds interest in its project's facts, a Git, worktrees or Code page, a task's Changes or Code tab and the merge dialog in its Git data too | a project no screen shows gets no facts or Git read at all; its board, sidebar row, badges, Inbox and question notifications follow its runtime events and the board read those events cause |
| Worker rows in a facts read | only for the task on view (its page, or the task previewed on a board) | a project on view with no task on view reads none; an explicit read for a project no screen shows still carries every started task's rows. Measured on a fixture of ten started tasks with three workers each: 184,921 bytes of worker rows for every task, 18,493 for the task on view |
| Facts reads while a task streams | only for a project on view with a task on view or a Git screen; at most one in flight per project, the next no sooner than 5 s after the last ended | updates in between collapse into one trailing read; a task on view whose state moves (phase, runtime or execution state, wait reason, execution) is read at once, so its workers arrive with that state; the repository is reread only with a Git screen on view, and then only when a task's state moved or the owner's own Git action made it stale; none while the window is hidden; the conversation and board updates themselves are not delayed |
| Event journal poll in the service | 500 ms after activity, doubling to 4 s while empty | any request to the project's child resets it |
| Opening a screen | once, as it opens or a parked tab is shown again | moving between pages of the same project and kind reads nothing more |
| Git screen on view | on open, after the owner's own Git action or a merge, on its Refresh Git status control, and every 30 s (`GIT_VISIBLE_REFRESH_MS`) while it is on view and the window focused | files change outside the app without any event, so this one light refresh stays; none while the window is hidden or another window has the focus; a failed repository read is retried on its own (3 s, doubling to 30 s) only while such a screen is on view |
| Return to the window | on focus or on becoming visible | rereads only the projects on view, and only what is older than 10 s (`FOCUS_STALE_MS`); facts reach the screens only when they differ, as data, from what the screens last received, and a project whose facts did not change keeps its records in place |
| Machine facts | about every 5 minutes, lined up with the engine limits snapshot, while the window is visible | the sidebar shows the engine limits, so this read stays; the machine overview is read when a screen that shows it opens (again only when older than 60 s), joins this poll only while such a screen is on view, and is never read at startup |
| Engine limits refresh in the service | one background pass when a settings read asks for it, at most one pass per 15 s, each connection at most once per 5 minutes | no thread runs between reads: with no window reading settings, no engine CLI starts |
| Sprint loop in the service | once per project at start or activation; on an owner or loop change of a sprint or task record; on a runtime task event while the project has a sprint in motion (a queue running, planning, or a result waiting for an automatic settle); every 30 s for such a project as a safety tick | at most one pass per project per 2 s however often it is woken; a project with no sprint in motion costs nothing between changes; automatic acceptance rides the same passes |
| Conversation history | only for the task on view (its page or board preview); once in full when it is opened, then only the rows written after the ones held, on its task stream events | at most one read in flight per project, the next right after it when more events arrived, never sooner than 120 ms after the previous began; a forward read seeks its position through the display tables' (session, seq) indexes, so it costs the same on a long conversation as on a short one (in-memory synthetic session, debug build: about 5,100 SQLite VM steps, 1.5–2 ms, to read 10 new rows after 200 or after 10,000 rows); a service without forward cursors gets the former whole reread; incomplete reads never cached |
| Working indicators | animated only while something is pending | a pressed control's bar sweeps by `transform` after 150 ms; a loader icon turns in 12 steps (0.9 s a turn while waiting for a reply or a page, 2.4 s for a long-running working status); all are removed when the work settles and paused in a parked tab or a hidden window; reduced motion pulses opacity every 2 s instead |
| Refresh on machine events | first event at once, the rest coalesced to one per 2 s, or 15 s while hidden | only the projects the events came from are reread |

What the queues change reaches the screens as a push notification from the child, not by rereading on a timer. Store signals and index stay the same objects when a read changes nothing. `createTicker` in `packages/workspace-ui/src/freshness.tsx` is the timer a screen should use: it stops when the window is hidden or the surrounding `ScreenActive` value is false, so a kept-alive screen that is not on view does no background work.

#### Proven costs and repairs

- Saved owner attachments, measured 2026-11-17 on an installed build: the private product state of one project held six owner messages with inline screenshots (4.9 MB of a 5.2 MB file). Every product call parsed the whole file, every save rewrote and synced it, and every `product.read` took 1.6 to 5.4 s and returned 5.7 MB to the window (`product.facts` 1.5 MB). Attachment bodies are now private content-addressed files beside that state (see [attachment files](consistency-and-recovery.md#attachment-files)); the state, every reply and every command carry a reference of about 150 bytes per file. With the same six messages as a fixture (six 600 KiB screenshots), the saved messages shrink from 4,916,468 to 1,748 bytes of JSON. Bytes are read only when the owner opens a file, or when the service hands the files to Core or builds a planning prompt. The installed timing after removing those payloads was 0.32 s and 0.8 MB per `product.read`; the remaining reply is per-task records and sprint plans, not attachment bytes.
- Repository snapshot (`repo.snapshot`), measured 2026-11-17 on a 1,560-file checkout with seven worktrees (three of them prunable), five saved task baselines on two old revisions and two recent commits that each touched about 1,600 files. The installed service took 6.3 to 11.7 s per call (once 24.8 s under load) for a reply of about 131 KB, and the window asks for it every few seconds. Per call it ran, for each distinct baseline, `diff --name-only` (about 0.45 s, spent in rename detection over about 1,400 added and deleted paths) and the rename-detecting `diff --unified=3` (about 0.5 s before its first bytes; the read then stopped at the display limit and reported the diff as over it), and `log -n 100 --shortstat` (1.2 s; the same `log` without statistics takes 10 ms). Measured on the same checkout with a test build of the changed code, the same task context and no other change: a first read after start 0.73 to 0.95 s (the statistics of one 1,601-file commit, about 0.63 s, bound it; later reads never compute them again), a read after a change 0.23 s, and an unchanged read 55 to 66 ms. The over-limit baselines are now decided in 10 to 15 ms each. The new reply equalled the installed service's reply field for field except two files another writer changed between the two reads. These are wall times of one test process, not measurements of the installed app.
- Full conversation replay: four executed tasks, 1,105 visible rows in 22 pages on the **same private database copy** took 1197.3164510000001 ms CPU with installed history code versus 302.5701240000001 ms with checkout code. This is measured CPU per complete read, not a process-percent prediction. The copy passed SQLite quick-check; source file stamps moved during copying, so it is diagnostic data, not an exact live snapshot. A separate stable copy also passed quick-check. Profiling attributed 2.524 of 2.973 seconds to repeated validation of growing page prefixes. Construction now validates single rows and the final page with additive UTF-8 byte accounting. Cursor, identity, unavailable-content and page-size checks remain.
- A conversation history page walked its whole session once per tool row. Each tool row merges its call's earlier updates, and that lookup used the session index only, so it ran `json_extract` on every earlier update of the session. One late page of a long task took seconds, and a whole conversation read grew with the square of its length. A running task's conversation is reread page by page after each change. Each page holds the project's single native read connection, and the 250 ms delta poll waits on that connection; the poll for every project waits for all of them. So one long conversation slowed reads and live updates across every project, and a read queued behind it could pass the desktop's 35 s request deadline (`service_timeout`). Measured on synthetic in-memory sessions with a release build, three updates per tool call and about 1.3 KB per update, before the change: the full read took 1.7 s at 1,500 updates, 6.5 s at 3,000, 21.4 s at 6,000 and 84.5 s at 12,000. The initializing schema now adds `host_updates_by_call` (see [runtime indexes](../project/storage.md#runtime-indexes-and-offloaded-worker-activity)), and the history and coordinator lookups use it. On smaller synthetic updates, full reads of 1,651, 3,151, 6,151 and 12,151 updates took 33, 62, 122 and 431 ms with the index. Without it they took 533, 1,755 and 7,079 ms; the 12,151-update read was not repeated without it. Pages read the same with and without the index. These figures were not measured on an owner store or in the installed app. The index is built once, the first time the runtime writer opens an existing store. On a private copy of one real `host_updates` table (59,766 updates, 43 MB, warm page cache), the build took 70 ms and added 3.5 MB, and the lookup plan then used `host_updates_by_call`.
- The window previously replayed every task's history on every refresh. Complete histories are reused until the task or execution changes, relevant journal events arrive, or the owner sends input. If the journal cannot be read completely, changed project history is reread conservatively; incomplete history reads are not cached.
- With a native board, every executed task's complete history was read inside one details read, and nothing was published until all of them finished with the watermark unchanged. On 2026-11-17 the installed service was measured with read-only `history.page` calls against a 3.2 GB release store without `host_updates_by_call`. Ten executed tasks held 7,872 visible rows, read in 92 pages. One complete pass took about 466 s, with the window's own reads running at the same time. Single pages took 0.1–15 s, and the longest conversation (1,554 rows, 18 pages) took 91 s. The board read itself took 2–9 s while it queued behind these pages. Any stream event in those minutes discarded the pass, so with a working task no conversation was ever shown. Conversations are now read and published per task, outside the details read (see [consistency and recovery](consistency-and-recovery.md)). The cost of one conversation read is unchanged by this; the per-tool-row lookup above sets it. History pages remain serial per project.
- A streaming conversation lagged by minutes and showed a message cut off mid-word. Each change of a running task reread its whole history from the first page, so the screen was always one complete reread old, and a message still being streamed was shown as of the chunk the last complete read reached; on the installed build a 1,554-row conversation took 18 pages. Every history page now names a forward cursor, and after the first complete read the window reads only the rows written after the ones it holds, driven by the task's stream events; only the conversation on view is read this way. A page's newest position is now taken from each table's own maximum through its index, and its rows from each table's (session, seq) index separately, merged in order; before, the newest position was a maximum over a union of the whole session. Measured with `cortex-core` `projections::history::tests::a_forward_reads_cost_does_not_grow_with_the_history_before_it` (in-memory synthetic sessions, debug build): reading 10 new rows took 5,193 SQLite VM steps (1.5 ms) after 200 rows and 5,056 (2.0 ms) after 10,000 rows. The installed app and an owner store were not measured. The service still notices a written row on its 250 ms delta poll, so a row reaches the open conversation within about that poll plus one forward read; this was not measured in the installed app.
- A long conversation showed nothing of its latest part for minutes after a restart. Its first read in a window paged `history.page` from the first row, 100 rows a request. One real task held about 22,000 rows in one session (13,270 updates and 8,965 transcript rows), so the first open after a service restart needed more than 220 sequential requests before the latest messages appeared. A first read now starts at the end with `history.earlier`. It reads at most four backward pages and stops once 150 rows are held, so that conversation opens after two requests. Earlier parts are read only when the reader scrolls near the top or presses Show earlier (see [consistency and recovery](consistency-and-recovery.md)). A backward page reads each display table through its (session, seq) index before its position. Measured with `cortex-core` `projections::history::tests::a_backward_read_seeks_and_does_not_grow_with_the_history` (in-memory synthetic sessions, debug build), the newest 100-row page took 40,102 SQLite VM steps on a 200-row session and 40,432 on a 10,000-row one. The Workspace UI `conversation-earlier` test bounds the first open of a 22,000-row scripted history at four requests. The installed app and an owner store were not measured.
- Slow Git completion previously emitted a full-refresh request. If the refresh outlasted the Git cache, it spawned another slow Git read and repeated. Completion now publishes facts, not another full task/history read. A superseded completion keeps the last confirmed facts until the next read of that screen. A failed repository read also keeps them, but while a screen showing that project's Git is on view it is retried on its own after 3 s, doubling up to 30 s, and a success publishes facts the same way; so a cause fixed outside the app (a folder's permissions, a Git lock) clears without a restart or an event. A refusal with an owner-readable reason (for example an unsafe private folder) is shown as the review's unavailable reason.
- Permanent status animations consumed frames with no progress. In the same 29,120-node fake worker view on private Xvfb, two `spin` animations produced 52.199276486711554% WebKit CPU, 18.7997394243329% GTK host CPU and 14.19980318220889% Xvfb CPU over 5.000069302999691 s. Disabling motion in that window reduced these to 5.999922910590467%, 0.3999948607060311%, 0 ticks. After static-indicator CSS, a fresh unmodified fixture measured 0.3999948493462252%, 0.1999974246731126%, 0 ticks respectively. The status words/icons remain; the busy control retains a delayed static underline. Actual streamed updates still paint.
- Static indicators made the window look frozen: a pressed control showed a still bar and a waiting page showed only words. Motion is back, bounded to what is pending. A loader exists in the page only while its work is pending, moves by `transform` or `opacity` alone on a small element, and turns in 12 discrete steps, so the page draws about 5 (working status) or 13 (reply wait) frames a second instead of 60. A parked tab and a hidden window (`html[data-hidden]`, set from `visibilitychange`) pause every loader, including the bar on the control's `::after`. `test/interface-rules.test.ts` fails any repeating animation outside these loaders or any loader keyframe that changes more than `transform` and `opacity`.

Reproduce the current no-paid UI measurement with `timeout 30 node packages/workspace-ui/test/webkit-cpu.mjs`. It builds production transforms and measures five windows on the 29,134-node fake worker view, isolated HOME/XDG and an automatically selected private display. It asserts that no animation runs with nothing pending, that a pending button runs `ws-busy-run` and stops when released, that a running task shows only the slow `spin`, that a hidden window runs none, and that at least three updates arrive. A writable Store open adds `task_events_by_activity_ref` and `runtime_requests_by_operation` without changing format 12. Non-initializing inspection/live opens never install them. Worker split-tool queries use `+assignment_ref` and `ORDER BY +id`: on this SQLite version, removing only ordering preference still let the assignment index win. The measured plan is `SEARCH task_events USING INDEX task_events_by_activity_ref (task_id=? AND <expr>=? AND id<?)`, with a temporary ordering B-tree. The regression compares complete before/after worker-page projections and checks the plan, not a hardware-dependent timing threshold.

The UI now settles action replies independently of reconciliation. Known task/sprint/checkout actions reread only their project, without capabilities or machine settings. Registry changes still reread those contracts. A newer reply fences older in-flight reads and requeues their scope, on success or error. An interrupted unscoped read retries with a full snapshot and matching facts, bypassing event-scope narrowing even if the adapter consumed the earlier invalidations. Synchronization stays pending through that replacement read. Facts notifications that arrive during a coherent read are applied after it when the port numbers its facts reads (`ProjectFacts.readOrder`, in the order the reads began): facts whose read began earlier than the installed ones are dropped, so they are never replayed over newer facts. Task-detail (enrichment) updates arriving during the read are likewise applied after it, version-checked. Neither starts another coherent read; before, a board read slower than the port's 100 ms presentation bound re-armed itself indefinitely and kept Updating confirmed state on screen. Unnumbered facts still queue a follow-up read of their project; duplicate notifications coalesce, and unchanged later polls need not notify again. The notice clears once the late board and facts replies of the read have arrived (`WorkspacePort.presented`, bounded to 10 s). Starting title generation (`generate_title`) neither fences reads nor shows Updating confirmed state; its end rereads the project. If a queued event refresh is combined with explicit project scopes, it reads all projects rather than consuming those scopes through event narrowing. Ordinary non-overlapping event and action reads remain project-scoped; requested changes are never applied on refusal or unknown outcome. Confirmed renames and sprint queue controls display locally; Updating confirmed state distinguishes the subsequent read from action submission. Errors retain the last confirmed view and retry without replaying the command. Sprint routing uses already-read product identities rather than spawning sequential product reads across the registry. Planning/settings actions that depend on current sprint contents still reread that one product before changing it. Product reads compute repository presence, branch and common directory once per call (a 40-task regression requires three Git queries total, not per task).

The isolated SQL/initialization/count checks were the former Python test `test_workspace_performance` (removed; not reproducible today).

`npm --prefix packages/workspace-ui test -- test/store.test.ts test/real-port.test.ts`.

Remaining costs: the helper still starts a process per bundled read/action (no persistent pool or shipped bytecode added); worker activity still has per-tool queries and growing-prefix byte accounting; product attachment bodies still cross IPC; child requests and history replays remain serial; Store connection setup, outbox-driven version churn, repeated contract validation and the machine-wide owner-record lock remain. ## Sprint graph, recorded

The sprint plan's Graph view draws its tasks and edges as SVG and moves the whole drawing as one layer: a pan or a zoom gesture writes only that layer's transform, once per animation frame, and touches no signal. When the gesture has been still for 120 ms the drawing is redrawn at the new scale, with its detail level, label lengths and minimap visibility. Selection and search change only the classes that differ. Layout is a pure function of the plan's keys and dependencies, memoized on them.

## Scrolling, recorded

These are recorded facts from the scroll gate, not a qualification: `node packages/workspace-ui/test/scroll-perf.mjs <label> [surface…]`. It builds the static bundle with the layout gate's fake data made long (`scroll` in `test/layout-fit-fixture.tsx`) and runs `test/scroll-perf.driver.mjs` in the `cortex-workspace-rendered:ubuntu26.04` container: WebKitGTK 2.52.6 at 1440×900 with **compositing on, as the desktop window runs it**, software GL on a private Xvfb, not the owner's GPU or the Tauri window. On each surface it finds every element that scrolls more than 300 px and scrolls it three times: a scrollbar drag from one end to the other in 120 frames and back in 60 (twice: the first pass is the first look at never-painted content), and the real mouse wheel turned 24 notches each way through X (`xdotool`). A script installed before the page's own records frame intervals, the forced style/layout time at the start of each frame, the time of every scroll and wheel handler and ResizeObserver callback, and every DOM change. WebKitGTK gives page script no style-recalc or layout counters and its inspector server did not start in this build, so layout is measured as that forced-flush time. Page timers count whole milliseconds. `idle` instead watches pages untouched for 70 s; the `-live` surfaces scroll while the task streams one update every 400 ms, five times the service's coalesced pace. Limits are p95 ≤ 22 ms, no frame over 50 ms, at most 3 % of frames over 25 ms, scroll and wheel handlers ≤ 4 ms, an update taken in ≤ 8 ms; what does not meet them yet is listed in the script's `KNOWN` table as a ratchet, printed on every run, and fails the run if it gets worse. Evidence goes to the git-ignored `.design-evidence/conversation/scroll-perf/<label>`.

What was found, measured before and after on 2026-11-10 (fake data: 60-task sprint, 77-card project board, a 200-task sprint, 31 projects in the sidebar, a 300-turn conversation, a 1,500-note worker feed, a 4,000-line file, 400 commits, 40 changed files of 300 lines, 900 lines of terminal output):

| Cause | Evidence before | Change | After |
|---|---|---|---|
| The facts poll serialized every project's facts with `JSON.stringify` to compare them, then delivered every project's facts once more after the full read, and re-installing a project's facts moved its records to the end of each list, so the screens' structural sharing saw a changed state | a 1,268 ms and a 975 ms frame at 30 s and 60 s on an untouched board; 14,828 DOM changes (14,043 rewrites of an unchanged `class`), about 955 ms of serialization per round | facts compared as data (`same` in `src/stable.ts`), the full read's facts count as delivered, re-read records keep their place (`applyFacts`) | no frame over 25 ms and no DOM change in 70 s |
| Board columns and the list windowed their rows: each scroll event created, measured and re-placed cards, and corrected estimated heights mid-scroll | sprint board drag p95 42 ms, 7 frames over 50 ms, 516 DOM changes; list wheel 26 of 151 frames dropped | rows in normal flow (`RowList` in `src/kit.tsx`) | drag p95 18 ms, wheel 0–2 dropped frames, no DOM change and ~0 ms of handlers while scrolling, also with 200 cards |
| A streamed update re-ran every row of a long worker feed: thousands of `JSON.parse` errors thrown in `displayStep`, every step's presentation rebuilt, a new entry object and a woken memo for each of 1,500 rows | each update a 60–77 ms frame while scrolling (8 long frames per wheel pass); 46 ms average, 84 ms worst per update after the first part of the fix | non-object text skips `JSON.parse`; `feedOf` hands back unchanged entries; rows read only their own entry; per-record caches; the route is parsed once per address | 10 ms average, 18 ms worst per update; no long frame while wheeling |

After, in the same run: the sidebar, sprint plan list, Graph pan, git history, the review diff, the terminal and the code tree stay at p95 17–19 ms with no frame over 50 ms, as they did before. Not yet at target, and held by `KNOWN`:

- The first scrollbar jump to the far end of a 70,000–200,000 px history pays one 88–155 ms frame painting it, with or without compositing; later drags and the wheel are on time. Letting the engine skip off-screen rows (`content-visibility`) made it much worse (p95 74 ms, 122 long frames in the worker feed), because the feed's scroll owner measures rows. The 10,000-event target's viewport-bounded DOM is not built: a conversation renders every row.
- The code editor (CodeMirror) renders and measures what each scroll brings into view inside the scroll event: wheel p95 20–22 ms with 4–5 % of frames late, drag 13–49 % late, handlers up to 24 ms, the same before and after. Parsing the whole file ahead in small steps did not change it and was not kept.
- With an update every 400 ms the 1,500-note feed still drops 4–6 % of frames, and an update takes 10–18 ms, above the 8 ms limit.

The Tauri window on the owner's NVIDIA GPU, a touchpad, and Wayland were not measured.
