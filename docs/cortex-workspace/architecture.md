# Architecture

**Status: planned product architecture. The local desktop slice in the last section is built with its no-paid checks. Remote access (host, client, Android app, relay stack) is built and checked only by no-paid automated tests; push is not built. Nothing is verified on a physical Android device or through a relay, and no platform is qualified for release.**

The desktop (Tauri 2 / SolidJS) and the Android app are views, not authorities. By the owner's decision of 2026-11-17 the Android client is the same adaptive Solid interface in a phone shell inside a Tauri 2 Android app, not a separate React Native application ([mobile concepts](design/mobile-concepts.md)). A separate Rust/Tokio service on the Ubuntu machine owns authenticated connections, ACP child lifetime, files, Git, PTYs and language servers. It survives closing the UI, not machine shutdown. The Rust `cortex-acp` stdio entry and the Workspace machine service use the same native runtime and Core lifecycle. Clients use versioned projections and typed control requests. See the [runtime architecture](../project/architecture.md#incoming-rust-acp-adapter).

The service brokers generic ACP capabilities separately from Cortex extensions. Explicit project activation is required. Use compact summaries for boards and bounded, paged history for detail. Client actions are authenticated, versioned commands; typed outcomes and authoritative snapshots are displayed. Existing Paseo integration is reference material, not a dependency or a migration prerequisite. Exact runtime workspace ownership and write isolation must be established against current source before implementing file mutation.

## Local desktop slice (built)

The first implementation milestone is a local vertical slice ([roadmap](roadmap.md), M2): a real Tauri window, the Rust machine service and the real Cortex runtime, carrying one owner journey from project registration to a runtime result. Its boundaries are:

| Location | Responsibility |
|---|---|
| `apps/cortex-workspace-desktop/` | Solid entry and Tauri 2 shell: native bridge with a closed operation allowlist, capabilities, local-content navigation policy and `.deb` configuration. |
| `crates/workspace-service/` | Tokio service: project locator registry, authenticated local socket, single-instance lock, child supervision, bounded project PTYs and the ACP client. It hosts Core task/history projections and a reusable draft writer under a cooperative project/channel lease. The same service hosts native execution, review and verification. |
| `crates/workspace-protocol/` | Shared Rust envelope and DTO codecs for the shell and the service. No Tauri or WebKit dependency. |
| `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` | Exact Rust workspace and toolchain inputs. The default member is the headless protocol crate only; the service and the Tauri application are built and tested explicitly. |
| `crates/workspace-protocol/channels.json` | Compiled channel identities for packages, binaries, units, runtime, configuration and state. Each channel has its own [home project stores and checkout markers](backlog/CW-S12.md). |
| `packaging/container/`, `packaging/systemd/user/` | The container build for native targets and the `.deb` packager, and the foreground user-level units for each channel. Installing the package installs the units and per-user login-start symlinks. |
| `crates/cortex-xtask` (`scripts/cortex-xtask.sh build-deb`), `scripts/cortex-paseo-tools.sh clone-dev-settings` | The container build driver (dev by default; CI release on manual `main` runs; CI dev on manual `dev` runs) and the non-secret settings clone into the dev channel. |
| `packages/workspace-ui/` | Promoted accepted presentation: components, styles, router and theme preferences. It also holds the phone shell (`phone.tsx`, `phone-shell.ts`, `phone.css`) and the Remote access settings page (`remote-access.tsx`). |
| `crates/workspace-remote/` | Embedded remote access over `iroh` 1.4.1: the host half (identity, paired-device registry, pairing, the tunnel to the local socket) and the client half (device identity, pairing, tunnelled streams), the pairing-link format and the compiled-in default relay (`default-relay.txt`, empty). Unix targets only. |
| `crates/workspace-service/src/remote.rs`, `remote_policy.rs` | Starts the host with the service, the owner-only `remote.*` methods, and the closed allowlist of what a paired device may call. |
| `crates/workspace-client/` | The machine-service bridge and the request allowlist shared by the desktop and phone shells, with a desktop profile and a stricter phone profile; its `remote` feature connects the bridge through a paired remote connection. |
| `apps/cortex-workspace-android/` | The Tauri 2 Android app: the shared interface in its phone shell, a closed native command set, the QR scanner plugin, and the phone side of pairing and connection. It has no local machine. Built by `scripts/build-android-apk.sh`. |
| `deploy/relay/` | Docker Compose, `relay.toml` and a runbook for one self-hosted `iroh-relay` behind an existing Traefik ([self-hosted services](self-hosted-services.md)). |
| `packages/workspace-domain/` | Pure presentation invariants, worker activity types/tool-row projection and DTO-to-view-model mapping. It never executes lifecycle transitions or imports a host plugin. |
| `packages/workspace-contract/` | Generated TypeScript wire types, constants and shared valid and invalid fixtures. |
| `crates/workspace-protocol/schema/workspace.json` | Canonical versioned wire schema; the shared Rust types and the generated artifacts derive from it. |
| `crates/workspace-service`, `crates/cortex-core` | The native components that translate private runtime tables into public records: command ledger, projections, invalidation outbox and adapter-owned project metadata. |
| `scripts/cortex-xtask.sh generate-contract check|write` | Deterministic generation and check of the schema fingerprint, Rust and TypeScript types and shared fixtures. |

The service connects to the retained execution runtime through the public `_cortex/workspace` extension and generic ACP stdio connection. Task/history reads and draft creation (with or without attachments) now use its in-process Rust Core provider; native execution and engine-policy composition are not enabled. The local socket is the only service interface. The desktop shell never starts, stops or talks to an ACP child directly. Closing the window detaches the subscription and leaves the child running. The service runs as a user-level process from its complete bundled runtime. Package installation arranges login startup; the native desktop bridge starts its fixed channel unit when necessary. An explicitly opted-in [extracted Dev launch](../configuration.md#workspace-dev-extracted-package)
instead has a caller-managed service, private per-run XDG directories and no service-manager or
notification activation fallback. The webview never receives a general systemctl or process-spawn capability. The separate local-owner PTY surface exposes only open/output/input/resize/close and intentionally carries interactive shell authority ([security](security.md#owner-terminal-built-local-linux)). Local transport and the adapter decision are recorded in [ADR 0014](adr/0014-local-service-transport.md).

Workspace UI compiles only its own client code and framework-free shared packages, never `integrations/paseo`. `packages/workspace-ui/test/paseo-boundary.test.ts` checks the actual TypeScript program (including type-only imports and tests). Paseo retains self-contained copies of the pure presentation modules for its standalone plugin distribution; the same test requires byte-identical implementations, allowing only import-path/type-source adaptation for worker grouping. RPC schemas and Zod validation remain in the plugin, outside the Workspace compile graph.

Remote access ([remote access](remote-access.md), [roadmap](roadmap.md), M5 and M6) is built on top of the local desktop and is not qualified; push is not built. The service reaches a phone only through the paired-device tunnel, and every remote request passes the closed allowlist before it reaches the same local socket the desktop uses ([security](security.md#remote-access-built-not-qualified)). The desktop's own remote machine registry (desktop to desktop) is not built; the local machine stays the one machine the owner starts.

Remote-path infrastructure sits outside the desktop and phone applications. Two owner-operated container services are planned for one owner's server through Docker Compose: an `iroh-relay` fallback (its stack exists in `deploy/relay/` and is not deployed or verified) and a push gateway for metadata-only FCM signals (not built). Clients install nothing extra and use built-in default URLs that the user can override ([ADR 0011](adr/0011-self-hosted-relay-and-push-gateway.md), [self-hosted services](self-hosted-services.md)).
