# Changelog

Entries record changes as they were made. Files, commands and tests they name that belonged to the Python runtime (removed on 2026-11-16, see 1.0.6) are history, not current commands.

## 1.0.6 (unreleased)

A task in a plain project folder, in no Git repository, no longer stops right after its plan is accepted. The runtime's project observation (execution baseline, review packet change list, review and verification binding, completion and acceptance digests) listed the folder only through Git, so in a folder without a repository every observation was refused with `project_revision_unavailable` and the task stopped with a stop question that said the runtime "recorded no more detail". When Git itself answers "not a git repository" for the folder and the folder holds no `.git` entry, the folder is now observed by walking it, with the same hashing, private-store exclusions, nested-checkout handling, empty-directory rule and safety bounds as a repository; nothing is ignored without a repository. A repository, or a folder inside one, is observed by Git exactly as before (unchanged digests), and a repository Git cannot read still refuses. The stop question now explains `project_revision_unavailable` (a repository Git could not read) and every `project_unobservable_*` refusal (an unreadable file or folder, a file changing while read, too many files, an unrecordable path name) in the owner's language. No store change. Tests: `native_effects::tests::a_plain_folder_without_git_is_observed_by_a_walk`, `a_broken_repository_is_refused_not_walked`, `a_repository_and_the_same_plain_files_have_different_digests`, the `plain-folder` scenario of `crates/workspace-service/tests/native_sessions.rs`, `stop_notice::tests::every_runtime_stop_kind_explains_what_happened_and_each_answer`.

Every model is a concrete model, and a refresh no longer moves the reader. The Claude adapter's `default` entry named no concrete model, so a worker on it read "Claude · default": the catalogue refresh, the bundled preset, routing and the pickers no longer offer it, and a saved routing file or profile that still names it loads and is reported as no longer offered. The session-configured record now carries the engine's own display name for the model (`model_label`, an optional event field, no store change) and the worker route exposes it as `modelLabel`; one shared label resolves recorded name, then catalogue, then the id. A worker's expanded goal, the stop dialogs' reason, the MCP server panel's observed diff and the close dialog's choice were reset by any refresh that replaced their record; they now reset only for another record. A previewed Markdown file keeps the elements of unchanged blocks and the editor replaces only the changed span of a reloaded file, so a background refresh keeps the reading position. Markdown tables now keep their rows until a blank line or another block (a row may hold no pipe, as in GFM), follow the GFM delimiter row (one hyphen, colon alignment) and align their columns.

Background updates no longer rebuild what the owner is looking at. Every store read hands the screens new objects, and lists drawn from them by object identity redrew their rows, so the composer's `/` suggestions (commands and project skills) jumped back to the top and lost their highlight while a task worked. The suggestion list now keeps every option that still reads the same and holds its highlight by the option's key, not its position. An audit of every Workspace screen fixed the same class elsewhere: Search and actions (rows and highlight), Add project's folder rows, the Code tree and its search results, Git status, history and worktree rows (the worktree menu now acts on the current row), the Changes Show menu, the Open in menu, the Inspector's rows and worker links, the close dialog's consequences, open decisions outside the timeline, the narrow worker picker, an opened step's tool rows, the conflict file list, a question's note links, the Archive and Merge pickers, the sidebar usage bars and limits menu, the offline machine record, and Settings and orchestration lists, menus, tabs and segment controls (machines, limits, profiles, files, preview grid, routing models, MCP matrix and servers, sprint graph filters), the planning questions and the sprint deletion strip, and a file conflict polled from disk. With this, the Routing page's Add a preferred model menu no longer lists models that are already preferred: its filter never matched before. Test: `packages/workspace-ui/test/background-stability.test.tsx` opens, scrolls, highlights, focuses and types on Conversation (workers menu, `/` and `@` lists), Work details, Changes, Code, Board, Inbox, Search and actions, sprint planning and Settings, sends the same data again and then unrelated news, and requires the same nodes and state.

Worker reports follow their template, every worker gets its predecessors, acceptance and constraints in its brief, and what a worker was given is recorded. Across 138 reports of four project stores, 136 contained at most one section of their template and 44 of 46 reviews were filed under `implementation`, because the inline draft was always created as `implementation` and nothing checked sections; 12 of 89 dependent attempts had no predecessor id in their prompt (the ids lived only in the capsule's clipped `current_nodes`, whose alphabetically sorted results could lose `report_ref`), the capsule's `constraints` was empty in every capsule (the native runtime records owner messages as `USER_STEERING` events, which it never read), and no delivery table was written. Only a template's own guidance comment is refused (any `<!--` was before). Programs the owner's terminal finds are found by the Workspace service too. The installed service runs under the systemd user manager with the unit's fixed `PATH=/usr/local/bin:/usr/bin:/bin`, so `node`, `npm` and `npx` from nvm (added by `.bashrc`), and anything in `~/.local/bin`, `~/.cargo/bin` or another per-user tool folder, were invisible: plan admission refused checks with `verification_executable_unavailable`, Diagnostics reported "npm: Not found by the desktop service", and workers fell back to `node_modules/.bin`. The service now reads the owner's tool search path (`crates/workspace-service/src/tool_path.rs`): at start, in the background, and on Re-read from my shell, it runs the owner's login shell once as an interactive login shell (bash, zsh and POSIX shells with `-l -i -c`, fish with `--login --interactive --command`), with no terminal, stdin closed, a minimal environment, cwd = home and a 5-second limit that kills its process group, and keeps only the `PATH` printed between per-run markers. A failed, hung or unsupported shell falls back to the service's `PATH` plus the existing usual per-user tool folders (including nvm's default version from `~/.nvm/alias/default`), with the reason shown; start never waits for or fails on the read. Entries must be absolute existing folders that are not world-writable without the sticky bit and not in Cortex's private state; they are de-duplicated in order and capped (64 entries, 16 KiB), and a command's own project can add none beyond its `.venv/bin`, `venv/bin` and `node_modules/.bin`. Worker commands (passed to each command supervisor), the final verifier, plan and verification admission, `check_preflight`, uncontained MCP servers (`PATH` and bare command lookup) and Diagnostics use it; engines keep their bundled Node and the unit is unchanged. No mount is added and no write access widened: the command sandbox already shows the host filesystem. A new **Tool search path** section on the Diagnostics settings page shows the detected folders with the time they were read, the ignored entries with their reasons, and extra folders the owner adds or removes (saved as `toolPathExtra` in `machine.json` under the existing lock; maintenance actions `tool_path.read`, `tool_path.reread` and `tool_path.set_extra`, desktop only). Diagnostics names where Git, Node, npm and bubblewrap were found and from which kind of folder, lists Docker and `python3` as optional, and adds a Tool search path item. A change applies from each running task's next command. Desktop notifications come from the machine service, cover every moment that needs the owner, and a click opens what they are about. A message to a working task no longer throws away the running work, and an owner `deny-write:` rule takes effect again. Any message the owner sent to a task while workers, review or verification ran (desktop Send now or a sent queued message, an incoming ACP prompt or queued message) was recorded and then interrupted the task: every running worker, wait and channel was cancelled and the task went to recovery and replanned. Now such a message is recorded once and interrupts nothing; the task keeps its state and the coordinator receives the message, with its attachments, at the next boundary of its own work: right after a planning turn (a plan that has not started is replaced), or when the revision reaches reconciliation after its verification passed (or earlier when the runtime returns to the coordinator anyway). Messages reach the coordinator in order (`STEERING_APPLIED`, `STEERING_HANDED`), are recorded delivered once the engine answered the prompt that carried them (`STEERING_DELIVERED`), are handed again (marked repeated) when a turn or the service ended before that reply, and a result never completes past one still waiting. A worker's open question no longer turns a message into an interruption: the question stays open and answerable. Desktop Queue messages are now sent by the Workspace service at the coordinator's next step, window open or closed, in queue order; they stay editable until taken (`sending`, then `message_taken`). Stop, Pause, worker Stop and command stop are unchanged; a message to a task whose coordinator waits for the owner, is held, paused or finished keeps its previous delivery. Each owner message in the conversation now reads "Taken from the queue for delivery", "Received, waiting for the coordinator's next step" or "Delivered to the coordinator" with the time, from runtime facts. A long conversation opens on its latest part, and earlier parts are read when the reader asks for them. A first read paged `history.page` from the first row, 100 rows a request, so a task with about 22,000 retained rows needed more than 220 sequential requests after a restart before anything of its latest conversation showed. The native read API adds `history.earlier`. Without a cursor it returns the newest rows of the session in source order, with the usual `tailCursor`; with its `prevCursor` it returns the rows before. It uses the same page bound, allowlist, session binding, `invalid_cursor` and `history_reset` semantics, and indexed reads before the position. `history.page` and every caller that reads forward (ACP host, Paseo tools, wire-1 queries) are unchanged. The window reads a fresh conversation backwards (at most four pages, until 150 rows are held) and then continues forward through the tail cursor as before. Owner actions no longer stall behind a merge, a pull request or a slow Git action. Merge, pull request and same-branch commit integration, and finishing or aborting a retained merge, hold the Workspace machine lock only to admit the request (the saved task record is checked again under it, and the durable operation intent is written) and for each short save of that task's record; Git, its hooks and GitHub CLI run after the lock is released, and a save keeps every other edit made meanwhile. A save after Git writes only the fields the integration or merge owns, so a title or target edited meanwhile is kept, and it (like finishing the operation intent) waits for the machine lock without a time limit, so an effect that happened is always recorded. The old-task cleanup takes the machine lock one project at a time and skips a task whose merge is running. A fetch, pull, push or commit of a project names itself on that project's Git lock, so a second Git action there is refused at once with `git_in_progress`. A long holder's name is kept in a note beside its lock, so the package install, which runs in a separate maintenance process, makes resume, retry and prompt refuse at once with `maintenance_in_progress` instead of stalling; a note left by a process that is gone is ignored. Task and worker reads are fast on large projects. A worker page (`workers`) now reads only the requested task's worker rows; it no longer re-reads the saved records, their Git facts, the project folder and every result review that it never returned. A worker's tool steps are built from one pass over the session's retained updates instead of one session scan per tool call, and a task's command receipts are read once for all its workers. Product facts compare results with a digest-only folder observation (ignored files feed only the ignored digest, so they are no longer listed), observed while the saved records and the store are read; the empty-directory walk and the legacy selection's mask walk read a large tree with several threads and return the ordered walk's exact result; the legacy folder capture runs once per read instead of twice per completed result; and a ready-to-merge task's per-file Git checks run a few files at once and apply in path order. One rule of the folder digest changed, with a one-time effect after the upgrade: empty directories inside wholly Git-ignored folders no longer count, and an empty-directory walk that cannot complete (over 300,000 entries outside ignored folders, or an unreadable directory) now gives a digest that never matches another observation, instead of one that could match a different folder. Results checked after the upgrade are not affected. A folder whose walk cannot complete cannot have its results accepted until it can be observed in full. Acceptance, automatic acceptance, integration and check reruns observe the folder fresh; only presentation reads reuse an observation, while its change signal (which now also covers the directories holding listed files, so creating or removing an empty directory moves it) is unchanged. Automatic sprints accept a finished result by themselves. While a sprint's run mode is Automatic, the sprint service accepts a finished task whose runtime verification passed and that the owner has not resolved, when its result passes the same validator as a manual Accept: the same source version and digest, no open failed, not-run or unverified check, no evidence warning and complete evidence. The acceptance is stored with `"automatic": true`, shown as automatic in the task's review, result card and conversation, and the sprint then starts its next task. A result that does not pass is not accepted, and the queue pauses for the owner as before. The decision uses the sprint's current run mode, read under the machine lock in the same step that writes the acceptance: switching to Manual stops automatic acceptance of every result not yet accepted, even one that finished under Automatic, and keeps Accept as an owner action; switching to Automatic accepts the sprint's waiting results that pass. Automatic acceptance never waits for the machine lock: while another operation holds it, the background pass tries again two seconds later instead of reporting a busy state, and task completion no longer touches sprint state or that lock. Manual sprints cost the background pass no task read, folder scan or window refresh. Manual sprints keep Accept as an owner action, and merge or PR creation still needs owner confirmation.
